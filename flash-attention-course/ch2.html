Chapter 2 · GPU Architecture & CUDA Basics

Everything about Flash Attention's design is dictated by the shape of GPU hardware. This chapter builds that mental model from zero and ends with the tiled matmul — the kernel that Flash Attention generalizes.

2.1 The GPU is a throughput machine

A CPU core minimizes the latency of one instruction stream: big caches, branch prediction, out-of-order execution. A GPU instead maximizes throughput: it is built from dozens of Streaming Multiprocessors (SMs) — 36 on an RTX 2070, 108 on an A100, 132 on an H100 — each of which juggles thousands of lightweight threads. When some threads stall waiting for memory (which takes hundreds of clock cycles), the SM instantly switches to other threads that are ready. Latency isn't avoided; it's hidden under a flood of parallel work. This only works if you give the GPU vastly more threads than it has arithmetic units — a key reason "not enough parallel blocks" (poor occupancy, §2.7) is a first-class performance bug, and one that FlashAttention-2 specifically fixes over FA-1.

2.2 The CUDA programming model: threads, warps, blocks, grid

A CUDA kernel is a C++ function, marked __global__, executed simultaneously by many threads. The threads are organized in a two-level hierarchy you choose at launch time:

  • A grid of thread blocks (up to 3-D indices). Blocks are independent: they may run in any order, on any SM, with no way to synchronize with each other during the kernel. A block runs on exactly one SM, start to finish.
  • Each block contains up to 1024 threads (also indexable in 3-D). Threads in the same block can share fast on-chip memory and synchronize with a barrier.

Inside the kernel, each thread discovers who it is via built-in variables and almost always converts them to a global index:

__global__ void vec_add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // my unique element
    if (i < n) c[i] = a[i] + b[i];                   // guard: grid may overshoot n
}

// host code: ceil(n/256) blocks of 256 threads
vec_add<<<(n + 255) / 256, 256>>>(d_a, d_b, d_c, n);
Warps — the unit the hardware actually runs
The SM does not execute threads one by one. It executes warps: groups of 32 consecutive threads (threads 0–31, 32–63, … of a block) that march in lockstep, all executing the same instruction on different data (SIMT). Two consequences you must internalize:
  • Divergence: if threads within one warp take different if branches, the warp executes both paths serially, masking threads off — up to 32× slowdown. Branching that is uniform across a warp is free.
  • Memory requests are issued per warp, which is what makes the next section's coalescing rule possible.
Warps can also exchange data among their 32 lanes directly through registers (§2.6) — no memory involved. FlashAttention-2's "work partitioning" story (§4.5) is entirely about how warps within a block divide up a tile.

2.4 Global memory coalescing

When a warp executes a load, the hardware merges the 32 threads' addresses into as few 32-byte memory transactions as possible. If thread \(t\) reads ptr[base + t] — consecutive threads, consecutive addresses — the warp's 128 bytes arrive in 4 transactions: perfectly coalesced. If instead thread \(t\) reads ptr[t * stride] with a large stride, every thread needs its own transaction: up to 32× more traffic for the same useful data.

Practical rule for matrices stored row-major: let adjacent threads handle adjacent elements within a row (the last, contiguous index). You will see this rule shape every load loop in the Chapter 5 kernel.

A row-major matrix M of shape (R, C) is in global memory. Pattern A: thread \(t\) reads M[t][j] (a column). Pattern B: thread \(t\) reads M[i][t] (a row). Which is coalesced and why, in terms of what the warp's address pattern looks like? What's the worst-case traffic ratio between them?

Write each as a flat address: M[r][c] = M[r*C + c]. Which one makes the flat address consecutive in \(t\)?

B is coalesced: addresses are i*C + t — consecutive for consecutive lanes, so the warp's request collapses into ~4 transactions. A generates addresses t*C + j, stride \(C\) elements apart: with \(C \ge 32\), 32 separate transactions, each fetching 32 bytes to use only 4 — up to ~32× the traffic (8× if counting 32-byte sectors vs 4-byte use).

2.5 Shared memory and barriers

A block can allocate fast on-chip memory with __shared__, visible to all of the block's threads:

__shared__ float tile[64][64];          // 16 KB of this block's SM budget
tile[threadIdx.y][threadIdx.x] = ...;   // threads fill it cooperatively
__syncthreads();                        // barrier: wait until ALL threads wrote
float x = tile[k][threadIdx.x];         // now any thread may read any entry

__syncthreads() is a block-wide barrier. The discipline that you will use in every kernel in this course:

The load–sync–compute–sync rhythm
  1. Load: all threads cooperatively copy a tile from HBM into shared memory (coalesced!).
  2. __syncthreads() — nobody reads a tile entry someone else hasn't written yet.
  3. Compute: every thread reads the shared tile freely, many times. This is where the data reuse happens.
  4. __syncthreads() — nobody overwrites the tile for the next iteration while a slow thread is still reading it.
Forgetting barrier #2 gives wrong answers sometimes (a race); forgetting #1's coalescing gives right answers, slowly. Also beware: __syncthreads() must be reached by all threads of the block — never put it inside a branch that only some threads take.

One level deeper (optional now, revisited in §5.9): shared memory is divided into 32 banks (4-byte wide, addresses interleaved). If multiple threads of a warp hit different addresses in the same bank simultaneously, the accesses serialize ("bank conflict"). All threads reading the same address is fine — it broadcasts.

2.5b Thread synchronization: what barriers do and do not guarantee

CUDA synchronization is deliberately local. A normal kernel gives you three useful scopes:

PrimitiveScopeWhat it guaranteesWhat it does not guarantee
__syncwarp(mask)lanes in one warpNamed lanes reach the same point; their prior memory operations are visible to those lanesNo ordering with other warps in the block
__syncthreads()all threads in one blockEvery block thread reaches the barrier; shared/global writes before it are visible to block threads after itNo synchronization with other blocks
kernel boundarywhole launched gridAll blocks of kernel A finish before kernel B starts, if launched sequentially in the same streamIt costs a launch and forces intermediate data through global memory

The missing primitive is the most important one: there is no ordinary grid-wide barrier inside a kernel. Blocks are scheduled independently; some may not even start until others finish. If an algorithm needs every block to finish phase 1 before any block starts phase 2, the simple CUDA answer is two kernels. Deep-learning kernels avoid that split when possible because kernel boundaries destroy fusion: any intermediate that crosses the boundary must be written to and read from HBM.

Barrier rules that prevent deadlocks and races
  • Every thread in the block must reach every __syncthreads(). Do not put it inside if (row < N) unless every thread takes that branch. Instead, let out-of-range threads participate in loads/barriers and guard only the arithmetic or final store.
  • A barrier is not an atomic operation. If two threads write the same address before a barrier, the result is still a race. Use one writer, a reduction pattern, or an atomic.
  • A memory fence is not a barrier. Fences order one thread's memory operations; they do not wait for other threads. For this course, think "shared tile reuse requires __syncthreads()."
  • Warp-synchronous code is only safe at warp scope. If data moves between warps through shared memory, use __syncthreads(), not just a shuffle or an assumption about scheduling.

Atomics are the other synchronization tool you will meet in deep-learning CUDA. An operation like atomicAdd(&dQ[idx], val) makes a read-modify-write to one address indivisible, so concurrent updates are not lost. Atomics are correct but can serialize badly when many threads hit the same address. Flash Attention backward uses atomics only for the tensor whose accumulation direction cannot be kept local (§6.3); avoiding unnecessary atomics is part of the algorithm design.

You are writing a tiled kernel where threads with row >= N have no output element. The tile loop contains two __syncthreads(). Should those out-of-range threads skip the loop? Explain the deadlock risk, the correct structure, and which statements should still be guarded.

A barrier waits for every thread in the block, not just every useful thread.

They must not skip the loop if any path inside it reaches __syncthreads(). If useful threads enter the barrier while out-of-range threads returned early or took a different branch, the block can deadlock forever. Correct structure: all block threads execute the cooperative loads and both barriers; out-of-range threads load neutral values where needed and skip only row-specific arithmetic and final stores. In Chapter 5, ghost rows still help load \(K,V\) tiles and still synchronize, but they never write \(O\) or \(L\).

For each situation, choose the synchronization mechanism and justify it: (a) all threads in a block cooperatively filled a shared-memory tile; (b) two blocks both need to add into the same global gradient element; (c) every block must finish computing an intermediate before any block consumes it.

There is no normal in-kernel grid barrier. Blocks communicate safely only through global memory plus kernel ordering, or through atomics for individual addresses.

(a) __syncthreads(), because the producer and consumer threads are in the same block and the data is a shared tile. (b) An atomic add or a different work partitioning that gives one block ownership of that gradient element; without an atomic, one update can overwrite the other. (c) Split into two kernels in the same stream, unless using specialized cooperative-grid launches; the kernel boundary is the normal grid-wide synchronization point, but it forces the intermediate through HBM.

2.6 Worked example: tiled matrix multiplication

Compute \(C = AB\), all \(N\times N\), one thread per output element. The naive kernel:

__global__ void matmul_naive(const float* A, const float* B, float* C, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= N || col >= N) return;
    float acc = 0.f;
    for (int k = 0; k < N; k++)
        acc += A[row * N + k] * B[k * N + col];
    C[row * N + col] = acc;
}

In matmul_naive, how many times is each element of \(A\) loaded from memory over the whole computation (ignoring caches)? What is the total load traffic in elements? Then: if a block of \(T\times T\) threads first stages \(T \times T\) tiles of \(A\) and \(B\) in shared memory, by what factor does global traffic drop?

Element \(A[i][k]\) is needed by every thread computing row \(i\) of \(C\). How many such threads are there?
In the tiled version, a tile element is loaded from HBM once per block, then read from SRAM by \(T\) threads.

Each \(A[i][k]\) is needed by the \(N\) threads computing \(C[i][\cdot]\), so it is loaded \(N\) times: total traffic \(2N^3\) element-loads. With \(T\times T\) tiling, each block loads each tile element once and reuses it \(T\) times from shared memory, so traffic falls to \(2N^3/T\) — a factor-\(T\) reduction (e.g. 32×). This load-once-reuse-\(T\)-times pattern is exactly what Flash Attention does to \(K\) and \(V\) tiles.

Now the tiled version. Study it until every line is obvious — the Chapter 5 attention kernel reuses every idea here:

template<int T>                                   // tile size, e.g. 32
__global__ void matmul_tiled(const float* A, const float* B, float* C, int N) {
    __shared__ float As[T][T];
    __shared__ float Bs[T][T];
    int row = blockIdx.y * T + threadIdx.y;
    int col = blockIdx.x * T + threadIdx.x;
    float acc = 0.f;

    for (int t = 0; t < N; t += T) {              // march tiles along the k axis
        // cooperative, coalesced loads: threadIdx.x is the fast (contiguous) index
        As[threadIdx.y][threadIdx.x] =
            (row < N && t + threadIdx.x < N) ? A[row * N + t + threadIdx.x] : 0.f;
        Bs[threadIdx.y][threadIdx.x] =
            (t + threadIdx.y < N && col < N) ? B[(t + threadIdx.y) * N + col] : 0.f;
        __syncthreads();

        for (int k = 0; k < T; k++)
            acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];
        __syncthreads();
    }
    if (row < N && col < N) C[row * N + col] = acc;
}

Note three things: (1) the accumulator lives in a register across all tile iterations and is written to HBM exactly once at the end — Flash Attention does the same with the output row \(O_i\) and its softmax statistics; (2) out-of-range loads store 0, which is harmless for a sum — attention will instead use \(-\infty\) scores, harmless for a softmax; (3) both __syncthreads() are load-bearing.

Explain precisely what goes wrong if (a) the first __syncthreads() in the tile loop is removed; (b) the second one is removed. Which bug is a correctness bug in both cases?

Warps of the same block do not run in lockstep with each other — one warp can race ahead a whole loop iteration.

(a) A thread may read As[threadIdx.y][k] before the thread responsible for writing that entry has written it — it reads stale/garbage data. (b) A fast warp loops around and overwrites the tile for iteration \(t{+}T\) while a slow warp is still reading iteration \(t\)'s values. Both are data races and both corrupt results nondeterministically — the second one is the one people forget.

2.6b Warp-level reductions (shuffles)

Threads of a warp can read each other's registers directly with shuffle intrinsics — no shared memory, no barrier. The workhorse is __shfl_xor_sync(mask, v, offset): each lane receives v from the lane whose index differs by XOR offset. A butterfly over offsets 16, 8, 4, 2, 1 reduces across all 32 lanes in 5 steps, leaving the result in every lane:

__device__ float warp_max(float v) {
    for (int off = 16; off > 0; off >>= 1)
        v = fmaxf(v, __shfl_xor_sync(0xffffffffu, v, off));
    return v;                       // all 32 lanes now hold the warp max
}
__device__ float warp_sum(float v) {
    for (int off = 16; off > 0; off >>= 1)
        v += __shfl_xor_sync(0xffffffffu, v, off);
    return v;
}

Real FlashAttention-2 uses exactly these to compute row maxes and row sums when one attention row is spread across the lanes of a warp. Our teaching kernel in Chapter 5 assigns a whole row to one thread (so reductions are plain loops), then §5.9 shows where shuffles enter.

Write warp_sum from memory and explain why the XOR-butterfly pattern leaves the correct total in all 32 lanes after exactly 5 steps.

After the off=16 step, lane \(i\) holds the sum of lanes \(i\) and \(i\oplus 16\). What invariant holds after each subsequent step?

Code above. Invariant: after processing offset \(2^k\), every lane holds the sum over all lanes that agree with it on bit positions below the ones processed — i.e. after offsets 16,8,4,2,1 each lane has summed over all 32 lanes (each step doubles the group size: 2, 4, 8, 16, 32). Since every lane performs the same combine, all lanes end with the full sum, which is exactly what you want when every lane needs the softmax denominator.

2.7 Occupancy, registers, and the shared-memory budget

An SM can host multiple resident blocks simultaneously, which is where latency-hiding parallelism comes from — but only if the blocks fit. Three budgets are shared by all resident blocks of an SM:

  • Threads: max ~1024–2048 resident threads per SM.
  • Registers: 65,536 per SM. A 256-thread block whose threads use 128 registers each consumes 32K registers — only 2 such blocks fit. Exceed 255 registers per thread and the compiler spills to (slow, HBM-backed) "local memory".
  • Shared memory: the per-SM pool (§2.3 table). One important quirk: a kernel using statically declared __shared__ arrays is limited to 48 KB per block for portability; to use more you must allocate it dynamically and opt in with cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, bytes). Real FlashAttention-2 does this; our teaching kernel stays under 48 KB.

Occupancy = resident warps ÷ maximum resident warps. Low occupancy is fine for compute-saturated kernels but deadly for memory-heavy ones, which need many warps in flight to hide HBM latency. Equally important at a larger scale: the grid must contain enough blocks to feed every SM — a grid of 8 blocks on a 108-SM A100 leaves 100 SMs idle no matter how good the kernel is. Hold that thought for §4.5.

A kernel uses two __shared__ arrays of float[64][64] each and runs blocks of 64 threads using ~180 registers per thread. (a) How much shared memory per block? (b) Does it satisfy the static limit? (c) On an SM with 64 KB of shared memory and 65,536 registers, how many blocks can be resident, and which resource binds?

One float[64][64] = 64·64·4 bytes.

(a) Each array is 16 KB → 32 KB per block. (b) Yes, 32 KB ≤ 48 KB static limit. (c) Shared memory allows ⌊64/32⌋ = 2 blocks; registers need 64·180 ≈ 11.5K per block, allowing 5 — so shared memory binds at 2 resident blocks (128 threads = 4 warps resident: low occupancy, acceptable only because each thread does a lot of independent work). These are precisely the numbers of the Chapter 5 kernel.

2.8 Performance fundamentals for deep-learning CUDA

Most deep-learning kernels are dense linear algebra plus reductions plus pointwise operations. A useful first pass is to classify the kernel by its limiting resource:

  • Memory-bound: low arithmetic intensity; runtime mostly tracks bytes moved. Examples: layer norm, softmax, dropout, many optimizer updates. Optimize by fusing kernels, coalescing loads/stores, vectorizing memory operations, and avoiding extra reads/writes.
  • Compute-bound: high arithmetic intensity; runtime mostly tracks math throughput. Examples: large GEMMs and convolutions. Optimize by using tensor cores, keeping operands reused on chip, and avoiding scalar side work in the inner loop.
  • Synchronization-bound or atomic-bound: enough math exists, but barriers, reductions, or atomics serialize progress. Optimize by changing the work partitioning so each warp/block owns independent output regions.

For deep learning specifically, these ideas show up constantly:

LayoutsMake the dimension touched by neighboring lanes contiguousCoalesced HBM access is often the difference between a real kernel and a demo
FusionCombine cheap pointwise/reduction work with nearby expensive workA separate kernel launch usually means writing and rereading an intermediate from HBM

Mixed precisionStore/compute inputs in fp16/bf16 when appropriate; accumulate sensitive sums in fp32Tensor cores are fast, but reductions and softmax statistics need numerical headroom

Flash Attention is a case study in this table. Standard attention is memory-bound because it writes \(S\) and \(P\) to HBM. Flash Attention fuses score computation, softmax, and value accumulation into one tiled kernel; keeps \(K,V,O,m,\ell\) on chip; accepts extra recompute in backward; and designs the block/warp ownership so the expensive accumulators are mostly local rather than atomic.

(a) Memory-bound: a few FLOPs per loaded/stored element; fuse it with a neighboring op or vectorize/coalesce the pass. (b) Compute-bound if implemented well: use cuBLAS/tensor cores or a tensor-core tiled kernel. 2.9 Correctness, profiling, and the CUDA development loop

The fastest way to write a wrong CUDA kernel is to optimize before you can catch mistakes. The development loop for deep-learning CUDA should be boring:

  1. Start with a CPU or framework oracle. For Flash Attention, compare against naive attention on small \(N\).
  2. Test hostile shapes. Non-multiples of tile sizes, tiny \(N\), causal and non-causal paths, odd head dimensions, and batches/heads greater than one.
  3. Check errors with the right tolerance. fp32 accumulation should be tight; fp16/bf16 tensor-core paths need looser tolerances. Compare max error and relative error, not just "looks close."
  4. Synchronize when timing. Kernel launches are asynchronous; time with CUDA events or call cudaDeviceSynchronize() around the region under test.
  5. Profile after correctness. Use Nsight Compute or similar tools to inspect achieved bandwidth, occupancy, register spills, shared-memory bank conflicts, tensor-core utilization, and warp stalls.
Use libraries until the operation is special
For ordinary GEMM, convolution, reductions, and layer norm variants, production deep-learning code usually calls cuBLAS, cuDNN, CUTLASS, Triton, or a vendor kernel. You write custom CUDA when the operation has a special dataflow the library cannot express — exactly the situation for Flash Attention, where avoiding \(N^2\) HBM traffic requires fusing the whole attention pipeline around online softmax.
