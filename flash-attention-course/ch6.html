Chapter 6 · The Backward Pass

Training needs \(\partial\mathcal{L}/\partial Q, K, V\) given \(dO = \partial\mathcal{L}/\partial O\) — and the forward pass deliberately threw away the \(N\times N\) matrices the chain rule seems to require. Plan: derive the gradients, find the two scalars per row that summarize everything, recompute the rest, and put it all in a verified CUDA kernel.

6.1 What backward needs, and the recomputation bargain

The forward pass saved: \(Q, K, V, O\) (all \(\Theta(Nd)\)) and \(L = m + \log\ell\) (\(\Theta(N)\)). It did not save \(S\) or \(P\). But §3.5 showed every attention weight is reconstructible in one expression:

$$ P_{ij} = e^{S_{ij} - L_i}, \qquad S_{ij} = \tau\, q_i \cdot k_j .$$

So the backward pass recomputes each tile of \(S\) and \(P\) on the fly, exactly when needed, in SRAM — paying roughly the forward pass's score-matmul again (backward totals \(\approx 10 N^2 d\) FLOPs vs forward's \(4N^2d\)) to avoid ever materializing \(N^2\) values in HBM. Chapter 1's roofline says this is the right side of the trade: FLOPs are abundant, bytes are not. Bonus subtlety: using the stored \(L\) (rather than re-deriving row maxes tile-by-tile) means the backward needs no online-softmax recurrence at all — any tile of \(P\) can be computed exactly, in isolation, in any order. That freedom is what lets backward parallelize differently than forward.

From memory: what exactly does FA-2's forward save for backward, how is a tile of \(P\) reconstructed, and why does having \(L\) (as opposed to running \((m,\ell)\) statistics) make the backward's tiles order-independent?

\(L\) is a property of the whole row, already fully reduced.

Saved: \(Q, K, V, O, L\) — \(\Theta(Nd + N)\) total. Reconstruction: recompute \(S_{\text{tile}} = \tau Q_i K_j^\top\), then \(P_{\text{tile}} = \exp(S_{\text{tile}} - L_i)\), exact because \(e^{s-m}/\ell = e^{s-L}\). Since \(L_i\) already encodes the full row's max and denominator, no partial state needs to flow between tiles: every \((i,j)\) tile of \(P\) is computable independently — unlike the forward, where \((m, \ell)\) had to be carried sequentially across \(j\).

6.2 Deriving the gradients

Forward, per row where needed: \(S = \tau QK^\top\), \(P = \mathrm{softmax}(S)\), \(O = PV\). We use the convention \(dX := \partial\mathcal{L}/\partial X\) (same shape as \(X\)). Work backwards through the three steps.

Step 1: through \(O = PV\)

For a product \(C = AB\): \(dA = dC\,B^\top\) and \(dB = A^\top dC\). Applied here:

$$ dV = P^\top dO \;\in \mathbb{R}^{N\times d}, \qquad dP = dO\, V^\top \;\in \mathbb{R}^{N\times N}. $$

Step 2: through the row softmax

For one row, \(p = \mathrm{softmax}(s)\): \(\partial p_j / \partial s_c = p_j(\delta_{jc} - p_c)\) (differentiate \(p_j = e^{s_j}/\sum_k e^{s_k}\) — do it once in your life). Chain rule:

$$ ds_c = \sum_j dp_j\, p_j(\delta_{jc} - p_c) = p_c\Big(dp_c - \underbrace{\textstyle\sum_j p_j\, dp_j}_{\text{call it } D}\Big), $$

i.e. in matrix form, with \(D_i = \sum_j P_{ij}\, dP_{ij}\) (a length-\(N\) vector, one scalar per row):

$$ dS = P \circ (dP - D\,\mathbf{1}^\top). $$

Step 3: the \(D\) trick — and through \(S = \tau QK^\top\)

As written, \(D_i\) needs a full row of \(P\) and \(dP\) — an \(O(N)\) reduction per row that would couple all tiles. The rescue is a little identity. Substitute \(dP = dO V^\top\):

$$ D_i = \sum_j P_{ij} (dO\,V^\top)_{ij} = \sum_j P_{ij} \sum_k dO_{ik} V_{jk} = \sum_k dO_{ik} \underbrace{\sum_j P_{ij} V_{jk}}_{=\,O_{ik}} = \sum_k dO_{ik}\, O_{ik}. $$
The D trick
\(D = \mathrm{rowsum}(dO \circ O)\): the per-row reduction over \(N\) attention weights collapses into a per-row dot product of two length-\(d\) vectors we already have in HBM. Computable by a trivial standalone kernel before the main backward, stored as \(N\) floats alongside \(L\). FA-2 calls this the "preprocessing" step.

Finally, through \(S = \tau\, QK^\top\):

$$ dQ = \tau\, dS\, K, \qquad dK = \tau\, dS^\top Q. $$

From memory, derive: (a) \(dV\) and \(dP\) from \(O = PV\); (b) the row-softmax Jacobian \(\partial p_j/\partial s_c\), and from it the formula \(ds = p \circ (dp - D)\) with \(D = p^\top dp\). Shapes for everything.

(a) Memorize once: for \(C = AB\), \(dA = dC B^\top\), \(dB = A^\top dC\) — check it by matching shapes.
(b) Write \(p_j = e^{s_j}/Z\); differentiate with quotient rule, treating \(j = c\) and \(j \ne c\) cases together via \(\delta_{jc}\).

(a) \(dV = P^\top dO\) (\(N\times d\)), \(dP = dO V^\top\) (\(N\times N\)). (b) \(\partial p_j/\partial s_c = p_j \delta_{jc} - p_j p_c = p_j(\delta_{jc} - p_c)\); then \(ds_c = \sum_j dp_j p_j (\delta_{jc} - p_c) = p_c dp_c - p_c \sum_j p_j dp_j = p_c(dp_c - D)\) with scalar \(D = \sum_j p_j dp_j\) per row.

Prove the \(D\) trick from memory: \(\mathrm{rowsum}(P \circ dP) = \mathrm{rowsum}(dO \circ O)\). Why does this matter so much for a tiled backward pass?

Substitute \(dP = dO V^\top\) and swap the order of the two sums.

\(D_i = \sum_j P_{ij}(dO V^\top)_{ij} = \sum_j P_{ij}\sum_k dO_{ik}V_{jk} = \sum_k dO_{ik}\sum_j P_{ij}V_{jk} = \sum_k dO_{ik}O_{ik}\), using \(O = PV\). It matters because without it, computing any tile of \(dS\) would require first reducing \(dP \circ P\) across all column tiles of the row (a sequential dependency, like forward's \(\ell\)); with it, \(D\) comes from data of size \(\Theta(Nd)\) in a cheap preprocessing kernel, and every \((i,j)\) tile of the backward becomes fully independent.

6.3 The FA-2 backward algorithm

Look at the four outputs and where their reductions run:

  • \(dV_j = \sum_i P_{ij}^\top dO_i\) and \(dK_j = \tau\sum_i dS_{ij}^\top Q_i\): reductions over rows \(i\) — natural if a worker owns a column block and loops over row blocks.
  • \(dQ_i = \tau\sum_j dS_{ij} K_j\): a reduction over columns \(j\) — natural for a row-block worker.

No single loop direction makes all three local. FA-2 chooses column-parallel: one thread block per K/V block \(j\), looping over all query blocks \(i\). Then two of the three accumulations (\(dK_j, dV_j\)) live in fast memory and are written once, and only \(dQ\) — whose contributions arrive from every column worker — is accumulated in HBM with atomicAdd. (The alternative used by some implementations: a second pass, row-parallel, just for \(dQ\) — atomics-free but reads everything twice. Trade-offs, always.)

Algorithm: FA-2 backward
 0:  preprocess: D = rowsum(dO ∘ O)  (N floats)        ── tiny separate kernel
     dQ ← 0                                            ── atomicAdd target
     worker for key/value block j (one thread block):
 1:  load K_j, V_j (Bc×d) into SRAM;  dK_j ← 0, dV_j ← 0
 2:  for i = 1 … T_r:
 3:      load Q_i, dO_i (Br×d), L_i, D_i (Br) into SRAM
 4:      S = τ Q_i K_jᵀ                    ── recompute  (matmul 1)
 5:      P = exp(S − L_i)                  ── exact, no statistics needed
 6:      dV_j += Pᵀ dO_i                                 (matmul 2)
 7:      dP = dO_i V_jᵀ                                  (matmul 3)
 8:      dS = P ∘ (dP − D_i),  scaled by τ
 9:      dK_j += dSᵀ Q_i                                 (matmul 4)
10:      dQ_i += dS K_j   via atomicAdd to HBM           (matmul 5)
11:  write dK_j, dV_j to HBM

Why does FA-2's backward parallelize over K/V column blocks when its forward parallelized over query row blocks? Make the argument by listing, for each of \(dQ, dK, dV\), which loop direction its reduction runs over — and conclude which choice minimizes HBM-side accumulation.

Count: how many of the three outputs accumulate over rows? Over columns?

\(dK_j\) and \(dV_j\) sum over all query blocks \(i\) (row direction); \(dQ_i\) sums over all key blocks \(j\) (column direction). A column-parallel worker keeps two of three accumulators (\(dK_j, dV_j\)) local in registers/SRAM, leaving only \(dQ\) to be accumulated through HBM atomics; row-parallel would invert this, forcing two tensors (\(dK, dV\)) through atomics. Pick the direction that localizes more state: column-parallel. (Forward had no such conflict: its only output \(O_i\) reduces over columns, so row-parallel localized everything.)

Reproduce the 11-line backward algorithm from memory, including the preprocessing step, what is recomputed at lines 4–5, all five matmuls, and which write is atomic. (Same drill as §4.2 — this is what you'll code below.)

Per (j, i) tile pair: recompute S, P; then the four gradient lines in dependency order dV → dP → dS → (dK, dQ).

See the boxed algorithm. Checklist: \(D\) precomputed as \(\mathrm{rowsum}(dO\circ O)\); \(dQ\) zero-initialized; \(P = \exp(S - L)\) with no online statistics; \(dS = P\circ(dP - D)\cdot\tau\); \(dK_j, dV_j\) written once at the end; \(dQ\) via atomicAdd inside the loop.

6.4 The CUDA backward, workbook-style

Full verified program: code/flash_bwd.cu (it includes the Chapter 5 forward kernel, which generates the \(O\) and \(L\) that backward consumes). Mirroring §5.0's simplifications: fp32, scalar loops, and now one thread = one key/value column, block = \(B_c\) threads, grid = \((\lceil N/B_c\rceil, H, B)\).

Step 1 — the preprocessing kernel

Write bwd_preprocess: one thread per row computes \(D_i = \sum_k dO_{ik} O_{ik}\). Signature: (const float* dO, const float* O, float* D, int N), layout [B,H,N,d], grid \((\lceil N/256\rceil, H, B)\), block 256.

Same bh pointer-offset pattern as Chapter 5, then a d-length dot product.
template <int d>
__global__ void bwd_preprocess(const float* __restrict__ dO,
                               const float* __restrict__ O,
                               float* __restrict__ D, int N) {
    int row = blockIdx.x * blockDim.x + threadIdx.x;
    if (row >= N) return;
    size_t bh = (size_t)blockIdx.z * gridDim.y + blockIdx.y;
    const float* dOh = dO + bh * N * d + (size_t)row * d;
    const float* Oh  = O  + bh * N * d + (size_t)row * d;
    float acc = 0.f;
    for (int k = 0; k < d; k++) acc += dOh[k] * Oh[k];
    D[bh * N + row] = acc;
}

Step 2 — the main kernel's skeleton

Each thread owns column col = blockIdx.x * Bc + tid: it keeps that column's \(k, v\) vectors and \(dk, dv\) accumulators in registers, while the block cooperatively stages \(Q_i, dO_i\) tiles (and \(L_i, D_i\) vectors) in shared memory — the exact mirror image of Chapter 5. Causality note for the loop bound: column \(c\) is only visible to queries \(i \ge c\), so a causal worker starts its query loop at its own diagonal block: i_start = (blockIdx.x * Bc / Br) * Br, and skips rows with qrow < col inside diagonal tiles.

Step 3 — the inner loop (write this one yourself, it's the exam)

Thread state: kvec[d], vvec[d], dk[d], dv[d]; shared: Qs[Br][d], dOs[Br][d], Ls[Br], Ds[Br] (already loaded and barriered). Write the loop body over local rows r: recompute \(s\) and \(p\), update dv, compute dp, then ds, update dk, and atomically add to global dQ. Be precise about where scale (τ) appears — it enters in two places, and misplacing it is the classic bug.

τ location 1: inside the exponent (\(p = e^{\tau(q\cdot k) - L}\)) because \(S\) includes τ. Location 2: as a factor on \(ds\), because \(dQ = \tau\, dS K\) and \(dK = \tau\, dS^\top Q\) — fold it into ds once and both inherit it.
Per row, the five updates in dependency order: \(p\) → (\(dv\), \(dp\)) → \(ds\) → (\(dk\), atomic \(dq\)).
int r_max = min(Br, N - i0);
for (int r = 0; r < r_max; r++) {
    int qrow = i0 + r;
    if (causal && qrow < col) continue;        // this query can't see my key

    float s = 0.f;
    #pragma unroll
    for (int x = 0; x < d; x++) s += Qs[r][x] * kvec[x];
    float p = __expf(s * scale - Ls[r]);        // P_rc, exact (τ in exponent)

    float dp = 0.f;
    #pragma unroll
    for (int x = 0; x < d; x++) {
        dv[x] += p * dOs[r][x];                 // dV_c += P_rc · dO_r
        dp    += dOs[r][x] * vvec[x];           // dP_rc = dO_r · v_c
    }

    float ds = p * (dp - Ds[r]) * scale;        // dS_rc, τ folded in once

    #pragma unroll
    for (int x = 0; x < d; x++) {
        dk[x] += ds * Qs[r][x];                 // dK_c += dS_rc · q_r
        atomicAdd(&dQh[(size_t)qrow * d + x], ds * kvec[x]);   // dQ_r += dS_rc · k_c
    }
}

Why atomicAdd: every column block \(j\) contributes to the same rows of \(dQ\), and thread blocks cannot synchronize with each other (§2.2) — concurrent read-modify-writes to dQ[qrow] from different blocks would race. Note the consequence you can observe: atomics make \(dQ\) bitwise nondeterministic across runs (float addition isn't associative), which is why frameworks expose "deterministic" modes that use the slower two-pass strategy instead.

Classic failure modes: forgetting to zero \(dQ\) (huge errors, only on the second run!); τ applied to \(p\)'s exponent but not \(ds\) (≈\(\sqrt d\)-scaled errors on \(dQ, dK\) only); using i_start but forgetting the per-row qrow < col skip (causal-only failures); barrier bugs if a thread continues across the __syncthreads() (keep barriers outside the per-row loop).

6.5 What the real implementation adds

Everything from §5.7 (tensor cores for all five matmuls, warp partitioning, async pipelining) plus two backward-specific notes: (1) real FA-2 stages \(dS\) tiles through shared memory so both \(dS^\top Q\) and \(dS\,K\) run as tensor-core matmuls — our per-scalar ds never exists as a tile; (2) the \(dQ\) atomics contend in L2; production kernels amortize them by accumulating a whole \(B_r \times d\) tile of \(dQ\) contributions in registers/smem per (i, j) pair and issuing one atomic add per element per tile rather than per row-column pair — same asymptotics, far fewer atomic operations than our teaching version.
