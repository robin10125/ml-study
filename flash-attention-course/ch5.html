Chapter 5 · FA-2 Forward Pass in CUDA

This is a workbook. You will build a complete, compilable FlashAttention-2-style forward kernel in five steps, writing each piece before seeing it. The finished program (code/flash_fwd.cu) compiles with nvcc -O3 -arch=native and passes verification against a CPU reference to ~1e-7 — it was tested on real hardware before being included here.

5.0 The spec — and what we simplify

We implement the 13-line algorithm of §4.2 with these choices:

ChoiceOur teaching kernelReal FlashAttention-2
Precisionfp32 everywherefp16/bf16 inputs, fp32 accumulators
Matmulsplain per-thread loopstensor cores (mma instructions via CUTLASS/CuTe)
Work splitone thread = one query row; block = \(B_r\) threadsone warp = a slice of query rows (split-Q, §4.4); 4–8 warps
Sizes\(d=64\), \(B_r=B_c=64\), template constantstuned per head-dim/GPU; smem > 48 KB via dynamic alloc
Layout[B, H, N, d] contiguous[B, N, H, d] (matches how QKV projections emerge)
Pipeliningnonecp.async overlaps next tile's loads with compute

Every simplification changes speed, none changes the algorithm: the grid mapping, the SRAM-resident tiles, the online-softmax inner loop, the single deferred normalization, and the \(L\) write are all exactly FA-2. §5.8 closes the gap to the real thing conceptually.

"One thread = one query row" deserves one comment: it works precisely because of §1.1 — softmax rows are independent, so a thread can carry its row's entire state \((m, \ell, o[d])\) privately in registers, and the only cooperation threads need is staging the shared \(K_j, V_j\) tiles. It is the same division of labor as FA-2's split-Q, just at thread rather than warp granularity.

Why can a single thread own a whole query row without ever synchronizing with other threads about softmax state — and what is then the only reason this kernel contains __syncthreads() at all?

What is shared between rows in the algorithm of §4.2? Only two tensors.

Row \(i\)'s statistics \((m_i, \ell_i)\) and output \(O_i\) depend only on row \(i\) of \(S\) — softmax rows are independent (§1.1) — so a thread's state never interacts with another thread's. The barriers exist solely for the cooperatively staged \(K_j, V_j\) tiles in shared memory: one barrier so nobody computes with a half-loaded tile, one so nobody overwrites a tile still being read (§2.5 rhythm).

5.1 Step 1 — launch configuration and indexing

Write first: the kernel signature, the grid/block mapping from §4.5, and the pointer arithmetic that gives each thread block its (batch, head) slice and each thread its query row. Inputs Q, K, V, outputs O (all [B,H,N,d]) and L ([B,H,N]), runtime int N, float scale.

Write: (a) the host-side dim3 grid(...) and block size for \(B\) batches, \(H\) heads, sequence length \(N\), row-block \(B_r\); (b) the first ~10 lines of the kernel: recover row (my global query index) and the five base pointers for my (batch, head). Mind integer overflow for large tensors.

Grid axes: x ← query block (the FA-2 sequence-parallel axis!), y ← head, z ← batch. Block: \(B_r\) threads, 1-D.
The (batch, head) pair flattens to bh = blockIdx.z * gridDim.y + blockIdx.y; each head slice holds N*d floats. Use size_t for the product.
// host:
dim3 grid((N + Br - 1) / Br, H, B);     // x: T_r query blocks, y: heads, z: batch
flash_fwd<D, BR, BC, false><<<grid, BR>>>(Q, K, V, O, L, N, scale);

// kernel:
const int tid = threadIdx.x;
const int row = blockIdx.x * Br + tid;            // my global query index

const size_t bh = (size_t)blockIdx.z * gridDim.y + blockIdx.y;
const float* Qh = Q + bh * N * d;
const float* Kh = K + bh * N * d;
const float* Vh = V + bh * N * d;
float*       Oh = O + bh * N * d;
float*       Lh = L + bh * N;

Grading notes: grid.x must be the rounded-up \(T_r\) (so row < N guards are needed later when \(N\) isn't a multiple of \(B_r\)); the size_t cast prevents 32-bit overflow at B·H·N·d ≳ 2³¹.

5.2 Step 2 — declarations and the cooperative K/V load

Per-block shared memory: the two streamed tiles. Per-thread registers: my query row, my accumulator, my score row, my statistics.

__shared__ float Ks[Bc][d];      // 64*64*4 = 16 KB
__shared__ float Vs[Bc][d];      // 16 KB   → 32 KB/block, under the 48 KB limit

float q[d], o[d], s[Bc];         // ~192 floats: near the 255-register ceiling;
float m = -INFINITY, l = 0.f;    // some spilling is acceptable in this version

if (row < N)
    for (int k = 0; k < d; k++) q[k] = Qh[(size_t)row * d + k];
for (int k = 0; k < d; k++) o[k] = 0.f;

Write first: the inner-loop opening — all \(B_r\) threads cooperatively copying the \(B_c \times d\) tiles \(K_j, V_j\) into Ks/Vs, with out-of-range rows zero-filled, followed by the barrier.

Write the cooperative load: \(B_c \cdot d = 4096\) elements, \(B_r = 64\) threads, so each thread moves 64 elements. Make consecutive threads touch consecutive addresses, guard rows past \(N\) with zeros, and place the barrier. Then answer: is your access pattern coalesced, and why?

Flatten: let each thread walk idx = tid; idx < Bc*d; idx += Br and split idx into row idx / d and column idx % d of the tile.
With this flattening, thread tid and tid+1 access global offsets that differ by exactly 1 float. That's the definition of coalesced.
for (int j0 = 0; j0 < N; j0 += Bc) {                  // KV-tile loop (line 3 of §4.2)
    for (int idx = tid; idx < Bc * d; idx += Br) {
        int r = idx / d, c = idx % d;
        bool in_range = (j0 + r) < N;
        Ks[r][c] = in_range ? Kh[(size_t)(j0 + r) * d + c] : 0.f;
        Vs[r][c] = in_range ? Vh[(size_t)(j0 + r) * d + c] : 0.f;
    }
    __syncthreads();
    ...

Coalesced: for a fixed strided-loop step, threads tid..tid+31 have consecutive idx, hence consecutive c within one tile row (since \(d = 64 \ge 32\) keeps a warp inside one row), hence consecutive global addresses → ~4 transactions per warp. The zero-fill is safe because a zero K row produces score 0 — but only because we also mask out-of-range columns with \(-\infty\) in step 3; the zero here just prevents reading garbage.

5.3 Step 3 — the score row, with masking

Write first: each thread computes its row of the score tile, \(s_c = \tau \,(q \cdot K_c)\) for \(c = 0..B_c{-}1\), tracking the tile row-max \(\tilde m\) as it goes, with two mask conditions applied by setting \(s_c = -\infty\): column out of range (\(j_0 + c \ge N\)), and — if causal — column in my future (\(j_0 + c \gt \text{row}\)).

Write the score loop (everything from here on sits inside if (row < N) { ... } — why inside, while the load loop above was not guarded?). Also recall from Chapter 3: why is \(-\infty\) the correct mask value rather than, say, a large negative constant or skipping the column?

Threads with row ≥ N still have to participate in the cooperative loads and barriers; they just must not write outputs.
What does \(e^{-\infty}\) contribute to \(\ell\) and \(o\) in the online update?
if (row < N) {
    float mt = -INFINITY;
    for (int c = 0; c < Bc; c++) {
        float dot = 0.f;
        #pragma unroll
        for (int k = 0; k < d; k++) dot += q[k] * Ks[c][k];
        bool masked = (j0 + c >= N) || (causal && j0 + c > row);
        s[c] = masked ? -INFINITY : dot * scale;
        mt = fmaxf(mt, s[c]);
    }

The load loop is unguarded because every thread of the block must reach __syncthreads() (§2.5) and the loads are useful work regardless of the thread's own row. \(-\infty\) is correct because \(e^{-\infty - m_{\text{new}}} = 0\): the masked column contributes exactly nothing to \(\ell\) or \(o\) with zero special-case code (§3 recall on edge cases). A finite constant like \(-10^9\) would contribute \(e^{-10^9 - m}\,{=}\,0\) too in practice but breaks \(L\)'s exactness guarantees in edge cases and is a famous source of subtle bugs when scales change. Note also Ks[c][k] is read by all threads at the same address simultaneously — a shared-memory broadcast, no bank conflict (§2.5).

5.4 Step 4 — the online softmax update (the heart)

Write first, from memory of §4.2 lines 6–11: given m, l, o[d], the fresh score row s[Bc] and its max mt, fold the tile in. Five small statements plus two loops. Then close the tile loop with the second barrier.

Write the update. Then trace it for the very first tile (where \(m = -\infty\), \(\ell = 0\)): what do alpha and the two rescales do, and why does no special "first tile" branch exist?

Order matters: compute m_new and alpha before touching l and o; update m last.
First tile: alpha = expf(-INFINITY - m_new) = 0.
    float m_new = fmaxf(m, mt);
    float alpha = __expf(m - m_new);      // history-repair factor (§3.4)
    l *= alpha;
    #pragma unroll
    for (int k = 0; k < d; k++) o[k] *= alpha;
    for (int c = 0; c < Bc; c++) {
        float p = __expf(s[c] - m_new);   // masked entries: exp(-inf) = 0
        l += p;
        #pragma unroll
        for (int k = 0; k < d; k++) o[k] += p * Vs[c][k];
    }
    m = m_new;
}                       // end of if (row < N)
__syncthreads();        // protect Ks/Vs from the next iteration's loads
}                       // end of j0 loop

First tile: alpha = 0 multiplies the empty history (\(\ell{=}0\), \(o{=}\mathbf 0\)) by zero — a no-op by construction, which is exactly why the \((-\infty, 0, \mathbf 0)\) initialization needs no special casing. The p·Vs loop is this kernel's hot spot: \(B_c \times d\) fused multiply-adds per tile per thread — in real FA-2 this and the score loop are the two tensor-core matmuls. (__expf is the fast hardware exponential; it's accurate to ~2 ulp which is plenty here.)

5.5 Step 5 — epilogue

Write first: after the tile loop — the FA-2 deferred normalization, the single output write, and the log-sum-exp write.

Write the epilogue. What exactly does each output row's HBM traffic total over the whole kernel, and which FA-2 improvement (of the three in §4.4) do these four lines embody?

Divide once. Write \(O\) once. Write one extra float per row.
if (row < N) {
    float inv = 1.f / l;
    for (int k = 0; k < d; k++) Oh[(size_t)row * d + k] = o[k] * inv;
    Lh[row] = m + logf(l);
}

Each output row is written to HBM exactly once (plus one float of \(L\)); it was never read back or partially written during the loop. The four lines embody improvement #1: normalization deferred to a single division (instead of per-tile renormalization), and only \(L = m + \log\ell\) stored for backward (instead of both \(m\) and \(\ell\)).

5.6 The complete verified program

The full file — kernel, CPU reference, and test harness over four configurations including non-multiple-of-tile sizes — is at code/flash_fwd.cu. The kernel in one piece:

template <int d, int Br, int Bc, bool causal>
__global__ void flash_fwd(const float* __restrict__ Q,
                          const float* __restrict__ K,
                          const float* __restrict__ V,
                          float* __restrict__ O,
                          float* __restrict__ L,
                          int N, float scale) {
    const int tid = threadIdx.x;
    const int row = blockIdx.x * Br + tid;          // my global query index

    const size_t bh = (size_t)blockIdx.z * gridDim.y + blockIdx.y;
    const float* Qh = Q + bh * N * d;
    const float* Kh = K + bh * N * d;
    const float* Vh = V + bh * N * d;
    float*       Oh = O + bh * N * d;
    float*       Lh = L + bh * N;

    __shared__ float Ks[Bc][d];
    __shared__ float Vs[Bc][d];

    float q[d], o[d], s[Bc];
    float m = -INFINITY, l = 0.f;

    if (row < N)
        for (int k = 0; k < d; k++) q[k] = Qh[(size_t)row * d + k];
    for (int k = 0; k < d; k++) o[k] = 0.f;

    // Causal: tiles strictly above the diagonal are skipped entirely (§4.6).
    const int j_end = causal ? min(N, blockIdx.x * Br + Br) : N;

    for (int j0 = 0; j0 < j_end; j0 += Bc) {
        for (int idx = tid; idx < Bc * d; idx += Br) {
            int r = idx / d, c = idx % d;
            bool in_range = (j0 + r) < N;
            Ks[r][c] = in_range ? Kh[(size_t)(j0 + r) * d + c] : 0.f;
            Vs[r][c] = in_range ? Vh[(size_t)(j0 + r) * d + c] : 0.f;
        }
        __syncthreads();

        if (row < N) {
            float mt = -INFINITY;
            for (int c = 0; c < Bc; c++) {
                float dot = 0.f;
                #pragma unroll
                for (int k = 0; k < d; k++) dot += q[k] * Ks[c][k];
                bool masked = (j0 + c >= N) || (causal && j0 + c > row);
                s[c] = masked ? -INFINITY : dot * scale;
                mt = fmaxf(mt, s[c]);
            }
            float m_new = fmaxf(m, mt);
            float alpha = __expf(m - m_new);
            l *= alpha;
            #pragma unroll
            for (int k = 0; k < d; k++) o[k] *= alpha;
            for (int c = 0; c < Bc; c++) {
                float p = __expf(s[c] - m_new);
                l += p;
                #pragma unroll
                for (int k = 0; k < d; k++) o[k] += p * Vs[c][k];
            }
            m = m_new;
        }
        __syncthreads();
    }

    if (row < N) {
        float inv = 1.f / l;
        for (int k = 0; k < d; k++) Oh[(size_t)row * d + k] = o[k] * inv;
        Lh[row] = m + logf(l);
    }
}

The causal support is exactly two lines of this kernel. Identify both from memory, explain each, and explain why the loop-bound line alone also guarantees the \(\alpha = \mathrm{nan}\) edge case (§3, fully-masked tile) can never occur.

One line changes how far the KV loop runs; one line adds a mask predicate per score.

(1) j_end = min(N, blockIdx.x*Br + Br): the KV loop stops at the diagonal block — "skip" tiles (§4.6) are never loaded or computed, giving the ~2× causal speedup. (2) causal && j0 + c > row in the mask predicate handles the diagonal-straddling tiles per element. No-NaN guarantee: the first visited tile (\(j_0 = 0\)) is never masked for any row, since key 0 is in every query's past — so \(m\) becomes finite on iteration one. Any later tile that happens to be fully masked for a particular row (possible when \(B_c \lt B_r\)) just yields \(\tilde m = -\infty\), \(m_{\text{new}} = m\) (still finite), \(\alpha = e^0 = 1\): a clean no-op, never \(-\infty - (-\infty)\).

5.7 From here to the real FlashAttention-2

What separates this ~70-line kernel from the production one (which is thousands of lines of CUTLASS/CuTe templates), in order of impact:

  1. Tensor cores. Our two inner matmuls (score loop, p·Vs loop) run on scalar FMA units. Real FA-2 issues mma.sync instructions on 16×8×16 fp16 fragments held in registers — ~16× more matmul throughput. This is also why it splits rows across warps rather than threads: a tensor-core op is a warp-cooperative instruction; the warp collectively owns a \(16\times B_c\) slice of \(S\), and the row max/sum are finished with the §2.6b shuffles across the few lanes sharing a row.
  2. Register pressure. Our q[64], o[64], s[64] ≈ 192+ floats/thread forces spills. The warp-cooperative layout shares these across 32 lanes (~6 floats each of \(o\), etc.), keeping everything truly register-resident.
  3. Async pipelining. cp.async (Ampere+) lets the block copy tile \(j{+}1\) HBM→smem while computing on tile \(j\) (double buffering: two smem tile buffers, alternating) — hiding essentially all load latency. On Hopper, the TMA unit and warp specialization (producer/consumer warps) push this further.
  4. Shared-memory swizzling. Tensor-core loads from smem hit bank conflicts unless the tile layout is permuted ("swizzled"); CUTLASS does this automatically. (Our kernel dodges conflicts by accident: its smem reads are broadcasts.)
  5. Bigger tiles, dynamic smem. \(B_r{=}128\) halves K/V traffic (§4.3) but needs >48 KB smem → dynamic allocation + cudaFuncSetAttribute opt-in (§2.7), and Q itself staged in smem rather than registers.

From memory, name at least four of the five techniques that separate the teaching kernel from production FA-2, and for each say in one phrase what cost it removes.

Think: arithmetic units, registers, latency, banks, tile size.

(1) Tensor cores — removes the ~16× matmul-throughput gap of scalar FMAs; (2) warp-cooperative tiling — removes register spills by sharing row state across 32 lanes; (3) cp.async double buffering — removes HBM load latency from the critical path; (4) smem swizzling — removes bank conflicts on tensor-core tile loads; (5) \(B_r = 128\) with dynamic smem — removes half the K/V HBM traffic.
