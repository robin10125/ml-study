Chapter 7 · Flash Attention in JAX

Two implementations: the FA-2 algorithm in pure JAX (a lax.scan + custom_vjp — runs anywhere, teaches the structure), and a real fused kernel in Pallas. Companion file code/flash_attention_jax.py is self-testing: 15 checks against naive attention and autodiff, all verified passing (Pallas runs in interpret=True mode on CPU, as a real Triton kernel on GPU).

7.1 Where kernels fit in JAX

In CUDA you control everything; in JAX you normally control nothing — you write jnp ops and XLA decides fusion, layout, and scheduling. XLA is good at fusing elementwise chains, but it will not invent flash attention from softmax(q @ k.T) @ v: the online-softmax restructuring is an algorithmic rewrite, not a peephole fusion. Your options, in increasing control:

LevelWhatWhen
1jax.nn.dot_product_attention(..., implementation="cudnn")Production on NVIDIA GPUs: dispatches to cuDNN's fused flash attention. Use this unless you have a reason not to.
2Blockwise algorithm in pure jnp (lax.scan)Algorithm research, TPUs/CPUs, custom attention variants; gets the memory win (no \(N^2\) materialization) but trusts XLA for speed
3Pallas: JAX's kernel DSL (lowers to Triton on GPU, Mosaic on TPU)You need real control of the grid/tiles — what this chapter teaches; jax.experimental.pallas.ops ships tuned attention kernels

Why can't XLA turn naive attention into flash attention on its own, and what specifically does the pure-JAX blockwise version (level 2) achieve versus what it leaves on the table?

What kind of transformation is the online softmax: local rewriting of operations, or a change to the algorithm's loop structure and intermediate values?

Flash attention replaces the computation's intermediates (full \(S, P\)) with a sequential recurrence carrying \((m, \ell, O)\) — a global algorithmic restructuring with different numerics ordering, which an op-fusing compiler won't derive. Level 2 expresses that recurrence explicitly, so no \(N\times N\) tensor ever exists → the \(O(N)\) memory win and the recomputation-based backward are achieved. Left on the table: explicit SRAM placement, tile sizing, and warp mapping — XLA may still schedule the scan suboptimally; that control is exactly what Pallas (level 3) adds.

Driver (full version with causal masking in the companion file):

def flash_forward_scan(q, k, v, block_k=128, causal=False):
    N, d = q.shape
    scale = d ** -0.5
    Tc = N // block_k
    kb = k.reshape(Tc, block_k, d)
    vb = v.reshape(Tc, block_k, d)
    init = (jnp.full(N, -jnp.inf), jnp.zeros(N), jnp.zeros((N, d)))
    (m, l, acc), _ = jax.lax.scan(body, init, (jnp.arange(Tc), kb, vb))
    return acc / l[:, None], m + jnp.log(l)        # output and lse

Causal masking is three lines inside the body — build column ids from the tile index j and where in \(-\infty\): col_ids = j*block_k + jnp.arange(block_k), s = jnp.where(col_ids[None,:] > row_ids[:,None], -jnp.inf, s). Tile 0 is never fully masked for any row (key 0 is visible to everyone), so \(m\) is finite after the first step and \(\alpha\) is never \(\mathrm{nan}\) — the same argument as §5.6.

7.3 Owning the backward: jax.custom_vjp

If you let JAX differentiate flash_forward_scan automatically, it saves the residuals of every scan iteration — including each \(p\) tile, resurrecting \(O(N^2)\) memory. The fix is the same as in CUDA: declare our own backward that recomputes from \(L\). The machinery:

@partial(jax.custom_vjp, nondiff_argnums=(3, 4))      # block_k, causal: not differentiated
def flash_attention(q, k, v, block_k=128, causal=False):
    o, _ = flash_forward_scan(q, k, v, block_k, causal)
    return o

def _flash_fwd(q, k, v, block_k, causal):
    o, lse = flash_forward_scan(q, k, v, block_k, causal)
    return o, (q, k, v, o, lse)        # (primal output, residuals) — O(Nd + N) saved!

flash_attention.defvjp(_flash_fwd, _flash_bwd)

And the backward body is Chapter 6's algorithm with a beautiful correspondence: the scan over KV tiles is the column-parallel loop, per-tile dk_j, dv_j are emitted as scan outputs (stacked — they were local to the worker), while dq rides in the carry, accumulated across all tiles — the role atomicAdd played in CUDA. (One honest difference: scan is sequential on-device, so this expresses the algorithm but gets its GPU parallelism only from vmap over batch/heads; the column-parallel version is what the Pallas/CUDA kernels do.)

Write _flash_bwd's scan body from memory (non-causal). Available per step: q (N,d), do (N,d), lse (N,), D (N,) precomputed, tile kj, vj; carry dq. Emit (dk_j, dv_j). Six lines.

Order from Chapter 6: recompute \(s, p\) → \(dv_j\) → \(dp\) → \(ds\) (τ folded in) → \(dk_j\), and fold \(ds\,k_j\) into the carry.
D = jnp.sum(do * o, axis=1)                     # before the scan: the D trick

def body(dq, blk):
    j, kj, vj = blk
    s = (q @ kj.T) * scale
    p = jnp.exp(s - lse[:, None])               # exact P tile from lse
    dv_j = p.T @ do
    dp = do @ vj.T
    ds = p * (dp - D[:, None]) * scale
    dk_j = ds.T @ q
    dq = dq + ds @ kj                           # the "atomicAdd", as a carry
    return dq, (dk_j, dv_j)

dq, (dk, dv) = jax.lax.scan(body, jnp.zeros_like(q), (jnp.arange(Tc), kb, vb))
return dq, dk.reshape(N, d), dv.reshape(N, d)

(a) (primal_output, residuals) = (o, (q, k, v, o, lse)) — all \(O(Nd)\) or smaller; no \(p\) tiles, no \(s\) tiles, nothing per-iteration. (b) First, before the residuals and cotangent: def _flash_bwd(block_k, causal, res, do). (c) Autodiff of a scan saves each iteration's primals needed for its VJP — here the \((N \times block_k)\) tile \(p\) (or equivalents) for each of \(T_c\) iterations \(= O(N^2)\) total: exactly the memory blow-up flash attention exists to kill. custom_vjp replaces that with recomputation from lse.

7.4 A real kernel: Pallas

Pallas is "CUDA-shaped JAX": you write a kernel over Refs (mutable views of memory) and launch it over a grid; on GPU it lowers via Triton. The three concepts, mapped to what you already know:

PallasMeaningCUDA analogue (Ch. 5)
grid=(G,)launch G program instances; pl.program_id(0) = which one I amgrid of thread blocks; blockIdx.x
BlockSpec(block_shape, index_map)which tile of the array each instance sees: instance \(i\) gets the block at block index index_map(i) (units of blocks, not elements), staged into fast memory as its Refthe cooperative HBM→SRAM tile load + pointer offsets — written for you
o_ref[...] = x / ref[pl.dslice(a, n), :]write a Ref / read a dynamic slice of a Ref on demandstores to Oh / staged reads of Ks/Vs

Our launch: one program per query block (the FA-2 grid, minus batch/heads which vmap adds). Q and the outputs are pre-tiled by their BlockSpecs; K and V are handed over whole (block index 0 for every instance) and sliced tile-by-tile inside the loop — so the kernel body controls the streaming, exactly like Chapter 5's j0 loop:

o, lse = pl.pallas_call(
    kernel,
    grid=(N // block_q,),
    in_specs=[
        pl.BlockSpec((block_q, d), lambda i: (i, 0)),   # my Q tile
        pl.BlockSpec((N, d),       lambda i: (0, 0)),   # all of K, sliced inside
        pl.BlockSpec((N, d),       lambda i: (0, 0)),   # all of V, sliced inside
    ],
    out_specs=[
        pl.BlockSpec((block_q, d), lambda i: (i, 0)),   # my O tile
        pl.BlockSpec((block_q,),   lambda i: (i,)),     # my slice of lse
    ],
    out_shape=[
        jax.ShapeDtypeStruct((N, d), q.dtype),
        jax.ShapeDtypeStruct((N,), jnp.float32),
    ],
    interpret=interpret,        # True = run as plain JAX anywhere (debugging/CPU)
)(q, k, v)

Decode from memory: for instance \(i\) with block_q=64, exactly which rows of Q does BlockSpec((64, d), lambda i: (i, 0)) deliver to q_ref, and why is the index map's return not (i*64, 0)? And why do the K/V specs use lambda i: (0, 0) with the full array as the block?

index_map speaks in units of blocks; Pallas multiplies by the block shape itself.

Rows \([64i, 64i{+}64)\): the index map returns block coordinates, which Pallas scales by block_shape to get element offsets — returning (i*64, 0) would double-scale. K/V use block index 0 with block shape = full array so every instance can address all keys/values; the kernel then pulls one (block_k, d) tile at a time via k_ref[pl.dslice(j*block_k, block_k), :], keeping the streaming under the kernel's control exactly like the CUDA j0 loop. (Q, O, lse are genuinely per-instance tiles, so their specs do the slicing.)

Write first — the kernel body. It is §7.2's scan body inside a fori_loop, plus the Ref reads/writes:

Write the complete non-causal Pallas forward kernel: signature (q_ref, k_ref, v_ref, o_ref, lse_ref, *, block_k, scale), a fori_loop over KV tiles carrying (m, l, acc), final normalize + both Ref writes.

Carry init: jnp.full((block_q,), -jnp.inf), zeros, zeros — same trinity as always. Loop bound: kv_len // block_k.
Tile read: kj = k_ref[pl.dslice(j * block_k, block_k), :].
def _pallas_fwd_kernel(q_ref, k_ref, v_ref, o_ref, lse_ref, *, block_k, scale):
    block_q, d = q_ref.shape
    kv_len = k_ref.shape[0]
    q = q_ref[...]                                   # (block_q, d)

    def body(j, carry):
        m, l, acc = carry
        kj = k_ref[pl.dslice(j * block_k, block_k), :]
        vj = v_ref[pl.dslice(j * block_k, block_k), :]
        s = jnp.dot(q, kj.T) * scale                 # (block_q, block_k)
        m_new = jnp.maximum(m, jnp.max(s, axis=1))
        alpha = jnp.exp(m - m_new)
        p = jnp.exp(s - m_new[:, None])
        l = l * alpha + jnp.sum(p, axis=1)
        acc = acc * alpha[:, None] + jnp.dot(p, vj)
        return m_new, l, acc

    init = (jnp.full((block_q,), -jnp.inf, jnp.float32),
            jnp.zeros((block_q,), jnp.float32),
            jnp.zeros((block_q, d), jnp.float32))
    m, l, acc = jax.lax.fori_loop(0, kv_len // block_k, body, init)

    o_ref[...] = (acc / l[:, None]).astype(o_ref.dtype)
    lse_ref[...] = m + jnp.log(l)

Loop bound: how many KV tiles intersect the past of query block \(i\)? Ceil-divide \((i{+}1)\,\mathrm{block_q}\) by \(\mathrm{block_k}\).
Indices: jax.lax.broadcasted_iota(jnp.int32, (block_q, block_k), dim) with dim 0 for rows, 1 for cols.
i = pl.program_id(0)
num_tiles = ((i + 1) * block_q + block_k - 1) // block_k   # skip future tiles
...
# inside body, after computing s:
rows = i * block_q + jax.lax.broadcasted_iota(jnp.int32, (block_q, block_k), 0)
cols = j * block_k + jax.lax.broadcasted_iota(jnp.int32, (block_q, block_k), 1)
s = jnp.where(cols > rows, -jnp.inf, s)

  • Batch and heads: all our functions take one \((N, d)\) head; jax.vmap(jax.vmap(f)) lifts to \((B, h, N, d)\) — and under jit, vmapping a pallas_call extends the kernel grid rather than looping. (Production kernels put batch/heads in the grid explicitly, like our CUDA gridDim.y/z.)
  • Use the shipped kernels when you can: jax.nn.dot_product_attention(q, k, v, is_causal=True, implementation="cudnn") on GPU; jax.experimental.pallas.ops.gpu.attention.mha (Triton FA-2, with its own custom_vjp backward kernel); on TPU, splash/flash attention in pallas.ops.tpu. Cheapest correct thing first; only buy control when measurements demand it.

First check if level 1 (cuDNN / shipped Pallas ops) supports the variant — if yes, done. If not: level 2 — blockwise scan + custom_vjp with the modifier in the score tile; this already avoids \(O(N^2)\) memory, which at 32k is the difference between running and OOM. Profile; only if XLA's scan scheduling is the bottleneck, write the Pallas kernel (level 3), reusing the level-2 implementation as the oracle. Gates at every level: (1) forward vs naive (small \(N\)), (2) lse vs logsumexp, (3) grads vs autodiff-through-naive — all with both causal and non-causal, and a non-multiple-of-block \(N\) if supported.
