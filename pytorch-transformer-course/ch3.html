Chapter 3 · nn.Module: Parameters, Buffers & Submodules

A PyTorch model is a tree of nn.Modules. The class does a surprising amount of quiet bookkeeping — collecting parameters, moving tensors between devices, switching train/eval behavior — and the whole thing rests on one magic method intercepting attribute assignment. Once you see the mechanism, building a transformer out of modules is just nesting.

3.1 The anatomy of a Module

Every model component subclasses nn.Module and defines two methods: __init__ (create the layers and weights) and forward (the computation). You call the module like a function; PyTorch routes that to forward:

import torch.nn as nn

class Linear(nn.Module):
    def __init__(self, n_in, n_out):
        super().__init__()                       # MUST come first
        self.weight = nn.Parameter(torch.randn(n_out, n_in) * 0.02)
        self.bias = nn.Parameter(torch.zeros(n_out))

    def forward(self, x):                        # x: (..., n_in)
        return x @ self.weight.T + self.bias     # (..., n_out)

layer = Linear(4, 3)
y = layer(x)            # calls layer.forward(x) — NEVER call .forward() yourself
Two non-negotiables

(1) Call super().__init__() first, before assigning any layer or parameter — it sets up the internal registries, and without it parameter tracking silently breaks. (2) Call the module, not .forward(): write layer(x), not layer.forward(x). The __call__ wrapper runs registered hooks and other machinery around forward; calling forward directly skips them.

3.2 nn.Parameter: a tensor the optimizer trains

An nn.Parameter is just a Tensor with requires_grad=True and one extra property: when you assign it as an attribute of a Module, the Module registers it as a trainable parameter. That registration is what makes model.parameters() — the list you hand to the optimizer — find it.

self.weight = nn.Parameter(torch.randn(3, 4))   # registered, trainable
self.scratch = torch.randn(3, 4)                 # a plain attribute — NOT registered
If it's not an nn.Parameter, the optimizer never sees it

Assign a bare torch.randn(...) as self.w and your forward pass works, but model.parameters() won't include it, so the optimizer never updates it and it stays at its random init forever — a model that "half-trains" for no visible reason. Any weight you want learned must be wrapped in nn.Parameter. (This is the requires_grad story from Chapter 2, now automated: nn.Parameter sets the flag and registers the tensor.)

3.3 Submodules register automatically — the __setattr__ trick

The same magic extends to whole modules. Assign an nn.Module as an attribute of another and it becomes a submodule; its parameters are now part of the parent's parameters(), recursively:

class Block(nn.Module):
    def __init__(self, d):
        super().__init__()
        self.ln = nn.LayerNorm(d)        # submodule
        self.fc = nn.Linear(d, d)        # submodule

    def forward(self, x):
        return self.fc(self.ln(x))

block = Block(8)
sum(p.numel() for p in block.parameters())   # counts ln's AND fc's params

This works because nn.Module overrides __setattr__: every time you write self.something = value, it checks whether value is a Parameter or a Module and files it in the right internal dict. That single mechanism is the whole tree: a model is modules holding modules holding parameters, and one call to model.parameters() walks it all.

A plain Python list of modules is invisible — use nn.ModuleList

self.layers = [nn.Linear(8, 8) for _ in range(3)] stores the modules in an ordinary list, which __setattr__ does not introspect — so those three layers are not registered, their parameters don't appear in parameters(), and they don't train. Wrap the list in nn.ModuleList(...) (for indexing/iteration) or nn.Sequential(...) (to chain automatically). Same trap for dicts → nn.ModuleDict. Your transformer's stack of blocks must be a ModuleList.

self.blocks = nn.ModuleList([Block(8) for _ in range(3)])   # registered
for blk in self.blocks:        # iterate like a list
    x = blk(x)

3.4 Buffers: state that isn't trained

Sometimes a module needs persistent tensor state that should move with the model (.to(device), save/load) but is not a trained parameter — a causal mask, running statistics, positional constants. That's a buffer:

self.register_buffer("mask", torch.tril(torch.ones(T, T)))
# self.mask now exists, moves with .to(device), is saved in state_dict,
# but has requires_grad=False and is NOT in parameters() — never trained.

The distinction: nn.Parameter = learned (in parameters(), gets gradients); buffer = fixed state (in state_dict, no gradients). A causal attention mask is the canonical buffer — it's a constant the model carries around, not something to optimize. (You can also just rebuild the mask in forward each call, as our reference code does; a buffer saves recomputation.)

You rarely hand-roll Linear — PyTorch ships the building blocks. The four that make up a transformer:

lin = nn.Linear(4, 3)      # bias=True by default; pass bias=False to drop it
lin.weight.shape           # (3, 4) — note: (out, in). forward does x @ weight.T
emb = nn.Embedding(46, 8)  # a lookup table; emb(ids) == emb.weight[ids]

Note the two surprises new users hit: nn.Linear stores its weight as (out, in) (so the forward is x @ W.T), and nn.Embedding is literally the fancy-indexing gather from Chapter 1 wrapped as a trainable module — emb(ids) equals emb.weight[ids].

3.6 nn.X vs F.x — modules vs functions

Many operations come in two forms: a module (capital, e.g. nn.ReLU, nn.Softmax) and a function (torch.nn.functional as F, e.g. F.relu, F.softmax). They compute the same thing. The rule:

Module form for things with state; functional form for pure ops

Use the nn. module when the operation owns parameters or buffers you want registered and managed — nn.Linear, nn.Embedding, nn.LayerNorm. Use the F. function for stateless math you just apply in forward — F.relu, F.gelu, F.softmax, F.cross_entropy. Activations have no weights, so calling F.gelu(x) in forward is cleaner than registering an nn.GELU() submodule. (Both are fine; this is the convention you'll see in real code, including ours.)

import torch.nn.functional as F
# in forward:
x = F.gelu(self.fc1(x))           # functional activation, no state
w = F.softmax(scores, dim=-1)     # functional, must pass dim

3.7 Lifecycle: to(device), train/eval, state_dict

Because a Module knows all its parameters and buffers, three whole-model operations are one call each:

model.to(device)        # move every parameter & buffer to a device (in place)
model.train()           # set training mode (dropout on, etc.)
model.eval()            # set eval mode (dropout off, batchnorm uses running stats)
sd = model.state_dict() # an OrderedDict {name: tensor} of all params + buffers
model.load_state_dict(sd)   # restore them — this is how you save/load weights
.train()/.eval() change behavior; no_grad changes recording — they're orthogonal

model.eval() flips a mode flag that layers like Dropout read (dropout becomes a no-op in eval). It does not turn off autograd. torch.no_grad() stops graph recording but does not change dropout. For evaluation/generation you usually want both: model.eval() for correct layer behavior and a no_grad block for speed. Forgetting .eval() means dropout randomly corrupts your generations; forgetting to switch back to .train() means your model stops learning. Our generate() is decorated @torch.no_grad() and calls model.eval() — both.

Build two models, each meant to hold three nn.Linear(8, 8) layers applied in sequence: model A stores them in a plain Python list self.layers = [...]; model B uses nn.ModuleList([...]). For each, print len(list(model.parameters())). Explain the difference and which one trains. (Each Linear has 2 parameter tensors.)

__setattr__ only introspects values that are themselves Parameters or Modules — a plain list isn't, so its contents go unregistered. ModuleList registers them.
class A(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = [nn.Linear(8, 8) for _ in range(3)]   # plain list!
    def forward(self, x):
        for l in self.layers: x = l(x)
        return x

class B(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = nn.ModuleList([nn.Linear(8, 8) for _ in range(3)])
    def forward(self, x):
        for l in self.layers: x = l(x)
        return x

len(list(A().parameters()))   # 0  -> layers NOT registered, won't train
len(list(B().parameters()))   # 6  -> 3 Linears x 2 tensors each
# A's forward still runs, but the optimizer never sees those weights, so
# they stay at random init forever. The stack of transformer blocks must
# be a ModuleList for exactly this reason.

Write a small module that, in __init__, stores a fixed (T, T) lower-triangular causal mask so that it (i) moves with model.to(device), (ii) appears in state_dict(), but (iii) is never trained and has no gradient. Then say, in a comment, why nn.Parameter would be the wrong choice here and why a plain self.mask = ... attribute would be a bug on GPU.

self.register_buffer("mask", torch.tril(torch.ones(T, T))). Parameter → it'd be trained (wrong). Plain attribute → it won't follow .to(device), so it stays on CPU and crashes a CUDA matmul.
class Masked(nn.Module):
    def __init__(self, T):
        super().__init__()
        self.register_buffer("mask",
                             torch.tril(torch.ones(T, T, dtype=torch.bool)))
    def forward(self, scores):            # scores: (..., T, T)
        return scores.masked_fill(~self.mask, float("-inf"))
# nn.Parameter: the mask would get gradients and be "trained" — nonsense,
#   it's a fixed structural constant.
# plain attribute: not registered, so model.to('cuda') leaves it on CPU;
#   the next masked_fill mixes CPU and CUDA tensors and raises. Buffers
#   move with the model; plain tensor attributes do not.
