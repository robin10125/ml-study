Chapter 2 · Autograd: backward(), .grad & no_grad

PyTorch trains models by recording every operation into a graph and walking it backwards. Most of the time this machinery is invisible — you call loss.backward() and gradients appear. But "invisible" is where the bugs live: forgotten zero_grad(), tensors that silently grow the graph, the .grad that's None. This chapter makes the machinery explicit so none of it surprises you.

2.1 requires_grad: opting a tensor into the graph

By default a tensor is just data. Set requires_grad=True and PyTorch starts recording every operation that uses it, building a graph it can later differentiate:

x = torch.tensor([2.0], requires_grad=True)
y = x ** 2 + 3 * x          # y is now a node that REMEMBERS it came from x
y.grad_fn                    # <AddBackward0> — the recorded operation

Any tensor produced from a requires_grad tensor inherits the flag and a grad_fn — a back-pointer to the operation that made it. Chains of these form the computation graph: a record of how the final scalar was computed, edge by edge, back to the inputs. nn.Parameter (Chapter 3) sets requires_grad=True for you, which is why model weights are trainable without you ever touching the flag.

2.2 What backward() actually does

Calling .backward() on a scalar walks the graph from that scalar back to every leaf with requires_grad=True, computing \(\partial(\text{scalar})/\partial(\text{leaf})\) by the chain rule, and deposits the result in each leaf's .grad attribute:

x = torch.tensor([2.0], requires_grad=True)
y = x ** 2 + 3 * x          # dy/dx = 2x + 3
y.backward()                 # walks the graph, fills x.grad
x.grad                       # tensor([7.])  — 2*2 + 3
Gradients are a side effect deposited in .grad

This is the central PyTorch idiom and the one most unlike a "pure" framework: backward() returns nothing. It mutates the .grad field of every leaf tensor as a side effect. The optimizer then reads those .grad fields to update the weights. So a training step is a three-party conversation: the loss's backward() writes .grad, the optimizer's step() reads it, and zero_grad() clears it for next time.

.backward() must be called on a scalar (a single number) — which your loss always is. On a non-scalar you'd have to pass a gradient vector (y.backward(v)), which you almost never do in training; if you see that error, you forgot to reduce your loss to a scalar with .mean() or .sum().

2.3 .grad accumulates — hence zero_grad()

Here is the behavior that bites every beginner: backward() adds to .grad; it does not overwrite it.

x = torch.tensor([1.0, 2.0], requires_grad=True)
(x ** 2).sum().backward()    # d/dx = 2x
x.grad                        # tensor([2., 4.])
(x ** 2).sum().backward()    # again — WITHOUT clearing
x.grad                        # tensor([4., 8.])  — DOUBLED, not recomputed

So between training steps you must reset gradients to zero, or each step's gradient piles onto the last and your updates are garbage:

optimizer.zero_grad()        # set every parameter's .grad to 0 (or None)
loss.backward()              # accumulate this step's gradient
optimizer.step()             # update using .grad
Forgetting zero_grad() is the #1 silent training bug

Nothing errors. Your gradients just accumulate across steps, so effectively your learning rate balloons and loss diverges or thrashes. If a training loop "explodes" for no clear reason, check that zero_grad() is there and is actually being called every step. (The accumulation isn't a mistake in the design — it's what lets you sum gradients over several mini-batches before stepping. But unless you want that, clear every step.)

2.4 Turning autograd off: no_grad, inference_mode, detach

Recording the graph costs memory and time. Whenever you're not going to call backward() — evaluation, generation, applying the optimizer update — you should switch recording off. Three tools, by scope:

with torch.no_grad():            # a block: nothing inside is recorded
    val_logits = model(val_x)    # forward pass with no graph, less memory

@torch.no_grad()                 # same thing as a decorator on a function
def generate(model, idx): ...

z = y.detach()                   # one tensor: z shares y's data but is
                                 # cut out of the graph (requires_grad=False)

torch.inference_mode() is a newer, stricter (slightly faster) version of no_grad for pure inference; no_grad is the safe default. Use a no_grad block around your whole eval/generation routine; use .detach() when you want to pull one value out of the graph mid-computation (e.g., to use a model's output as a fixed target).

detach vs .item() vs .data

x.detach() → a tensor sharing storage but off the graph (still on the GPU, still a tensor). x.item() → a single value pulled out as a plain Python float/int (only for one-element tensors; use it for logging). x.data → legacy, avoid: it bypasses autograd's safety checks. Reach for detach or item, never .data.

2.5 Leaf vs non-leaf, and why .grad is sometimes None

A leaf tensor is one you created directly with requires_grad=True (your parameters and inputs) — it sits at the edge of the graph. A non-leaf is any tensor computed from others (intermediate activations). After backward(), only leaves keep their .grad; intermediates' gradients are computed, used, and discarded to save memory.

x = torch.tensor([2.0], requires_grad=True)   # leaf
y = x * 3                                       # non-leaf
z = y.sum()
z.backward()
x.grad        # tensor([3.])  — kept
y.grad        # None + a warning — intermediates don't retain grad

Two more ways you end up with a surprising None gradient:

  • The tensor never had requires_grad=True — e.g. you built a parameter as a plain torch.randn(...) without wrapping it in nn.Parameter. No flag, no graph, no grad.
  • You broke the graph. Any .detach(), .item(), no_grad block, or conversion to NumPy in the path from parameter to loss severs the chain; gradient can't flow back through the cut. A model whose loss won't go down sometimes has an accidental .detach() in forward.

2.6 The shape of one training step

Everything above assembles into the loop you'll write for the rest of your life. Memorize the order:

optimizer.zero_grad()           # 1. clear last step's accumulated grads
logits = model(inputs)          # 2. forward — builds the graph
loss = loss_fn(logits, targets) # 3. a scalar at the graph's root
loss.backward()                 # 4. backward — fills every param's .grad
optimizer.step()                # 5. update params using .grad (under no_grad)

The optimizer was handed model.parameters() at construction, so it knows which tensors to read .grad from and update. Its step() mutates the weights in place inside its own no_grad region — which is the legitimate use of in-place ops from Chapter 1. Chapter 4 builds this loop out in full; for now, know that autograd's entire contract is steps 1, 4, and 5.

Then answer: what goes wrong if you swap the order of backward() and zero_grad()?

Order: zero_grad → forward → loss → backward → step. zero_grad must come before backward, or it wipes the gradient you just computed.
optimizer.zero_grad()            # clear last step's accumulated .grad
logits = model(inputs)           # forward: BUILDS the graph
loss = loss_fn(logits, targets)  # scalar root of the graph
loss.backward()                  # backward: WRITES .grad on every param
optimizer.step()                 # READS .grad, updates weights in place
# Swapping backward() and zero_grad(): zero_grad() would erase the gradient
# backward() just computed, so step() updates with zeros — the model never
# learns (and no error tells you).

You will type this loop hundreds of times. The only freedom in the order is that zero_grad may sit either at the very top or right after step — never between backward and step.
