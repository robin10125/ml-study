Chapter 6 · The Transformer in JAX

Chapter 5's diagram becomes ~80 lines of jax.numpy. Six functions: layer_norm, attention, mlp, block, forward, loss_fn — plus init_params. Every one is a recall below, and the same code lives verified in code/transformer.py. The convention throughout: B = batch, T = sequence, D = d_model = 128, H = 4 heads, head dim 32.

6.1 layer_norm

The smallest piece first. Statistics over the last axis with keepdims=True so the division broadcasts back over \((B, T, D)\):

def layer_norm(x, gamma, beta, eps=1e-5):
    mean = jnp.mean(x, axis=-1, keepdims=True)        # (B, T, 1)
    var = jnp.var(x, axis=-1, keepdims=True)          # (B, T, 1)
    return (x - mean) * jax.lax.rsqrt(var + eps) * gamma + beta

Self-check list: axis=-1 (per token, over features — never over batch or time); keepdims (or manual [..., None]) for the broadcast; \(\varepsilon\) inside the square root; \(\gamma, \beta\) of shape \((D,)\) broadcasting over the leading axes. jax.lax.rsqrt is a fused reciprocal square root — / jnp.sqrt(…) is equally correct.

Write layer_norm(x, gamma, beta, eps=1e-5) from memory for x: (B, T, D). Then state what each of these mistakes does at runtime: (a) axis=0; (b) omitting keepdims=True; (c) adding eps outside the sqrt.

Two reductions (mean, var), one normalize, one affine. The reductions must keep their axis so (B,T,1) broadcasts against (B,T,D).

Code as in §6.1. (a) axis=0 normalizes each feature across the batch — BatchNorm-ish, statistically wrong here, leaks across examples, and silently produces a working-looking model that trains worse. (b) Without keepdims the stats have shape (B,T) and broadcasting against (B,T,D) raises a shape error — the loud, kind failure. (c) rsqrt(var)+eps-style placement no longer guards the division: an all-constant token has var = 0 ⇒ rsqrt(0)=inf ⇒ NaNs that poison everything downstream.

6.2 attention: the centerpiece

Transcribing §5.2–5.4. The dance is: project → split heads → move the head axis forward → scores → mask → softmax → weighted sum → merge heads → output projection.

N_HEADS = 4   # static config — NOT inside params (see §6.5)

def attention(p, x):
    B, T, D = x.shape
    H = N_HEADS
    hd = D // H

    q = (x @ p["wq"]).reshape(B, T, H, hd).transpose(0, 2, 1, 3)  # (B,H,T,hd)
    k = (x @ p["wk"]).reshape(B, T, H, hd).transpose(0, 2, 1, 3)
    v = (x @ p["wv"]).reshape(B, T, H, hd).transpose(0, 2, 1, 3)

    scores = q @ k.transpose(0, 1, 3, 2) / jnp.sqrt(hd)           # (B,H,T,T)
    mask = jnp.tril(jnp.ones((T, T), dtype=bool))
    scores = jnp.where(mask, scores, -jnp.inf)                    # before softmax!
    weights = jax.nn.softmax(scores, axis=-1)

    out = (weights @ v).transpose(0, 2, 1, 3).reshape(B, T, D)    # merge heads
    return out @ p["wo"]

Why the transposes? @ on 4-D arrays batches over the leading axes and matmuls the last two. With heads at axis 1, q @ k^T means "for every (batch, head): a \((T, d_h) \times (d_h, T)\) matmul" — exactly the per-head score matrices, no vmap needed (though vmap over a single-head function is a fine alternative). Note the JAX specifics: the boolean tril mask is applied with jnp.where — the both-branches select from §3.2 — and \(-\infty\) is legal and exact (e^{-inf} = 0).

The centerpiece recall of the course: write attention(p, x) from memory — params wq, wk, wv, wo, all \((D, D)\); causal; multi-head. Annotate every line with its output shape. Then explain why q @ k.transpose(0,1,3,2) computes all B·H score matrices at once.

Order: project → reshape (B,T,H,hd) → transpose (B,H,T,hd) → scores /√hd → tril + where(−inf) → softmax → @v → transpose back → reshape (B,T,D) → @wo.
Matmul on n-D arrays: batch over all leading axes, contract the last axis of the left with the second-to-last of the right.

Code and shapes as in §6.2. Grade yourself against: reshape uses H and hd=D//H; transpose brings H before T (0,2,1,3); scale is \(\sqrt{d_h} = \sqrt{32}\), not \(\sqrt{D}\); mask built with jnp.tril(ones((T,T),bool)) and applied with where(mask, scores, -inf) before softmax; softmax over the last axis (keys); final transpose+reshape merges heads before wo. The batched matmul works because @ treats (B,H) as batch dimensions and contracts (T,hd)×(hd,T) → (T,T) per batch-head pair — B·H small matmuls expressed as one op.

6.3 mlp and block

def mlp(p, x):
    return jax.nn.gelu(x @ p["w1"] + p["b1"]) @ p["w2"] + p["b2"]

def block(p, x):
    x = x + attention(p["attn"], layer_norm(x, p["ln1_g"], p["ln1_b"]))
    x = x + mlp(p["mlp"], layer_norm(x, p["ln2_g"], p["ln2_b"]))
    return x

block is the pre-LN diagram verbatim: normalize inside the branch, add to the untouched stream. The two LayerNorms have separate learned \(\gamma/\beta\) (they normalize different statistics). Note how naturally the pure-function style composes: block takes its slice of the params tree and the stream, returns the new stream — no registration, no module tree, just function calls mirroring the dataflow.

Write mlp(p, x) (D→512→D, GELU) and block(p, x) (pre-LN, two residual adds) from memory, with the params layout they expect. Two audits: where exactly do the residual adds happen relative to the norms, and what would x = attention(p["attn"], layer_norm(...)) — without the x + — do to trainability at depth?

Pre-LN: LN sits at the entrance of each branch; the stream is only ever added to.

Code as in §6.3; params: {"ln1_g","ln1_b","ln2_g","ln2_b","attn":{wq,wk,wv,wo},"mlp":{w1,b1,w2,b2}}. The adds wrap each normalized branch: x + Attn(LN(x)) then x + MLP(LN(x)) — LN never applies to the through-path. Dropping x + removes the identity highway: gradients must then pass through every attention/MLP nonlinearity multiplicatively, shrinking layer by layer — the vanishing-signal regime that made deep pre-resnet networks untrainable. With the adds, the loss has a linear path to every layer's input.

6.4 forward: assembling the model

def forward(params, tokens):
    B, T = tokens.shape
    x = params["embed"][tokens] + params["pos"][:T]    # (B, T, D)
    for p in params["blocks"]:                          # unrolls under jit (§3.1)
        x = block(p, x)
    x = layer_norm(x, params["lnf_g"], params["lnf_b"])
    return x @ params["embed"].T                        # weight tying: (B, T, V)

Details worth noticing: params["embed"][tokens] is fancy-indexing a \((V, D)\) table with a \((B, T)\) int array — a pure gather, fully differentiable with respect to the table. params["pos"][:T] slices the position table to the actual sequence length and broadcasts over the batch. The Python for over blocks is fine: the list has fixed length, so under jit it unrolls into 3 copies of the block computation (a lax.scan over stacked layer params is the at-scale alternative — §4.5). Weight tying is literally .T.

Write forward(params, tokens) from memory. Then three whys: why is E[tokens] differentiable w.r.t. E even though it's indexing; why is the Python loop over blocks legal under jit (and when would you switch to scan); why does x @ params["embed"].T implement the unembedding, dimensionally?

Gather's gradient is scatter-add. Loop bound: traced or static? Shapes: (B,T,D) @ (D,V).

Code as in §6.4. ① A gather is a linear map (one-hot matmul without materializing the one-hot); its gradient scatter-adds each position's incoming gradient into the rows that were read — rows of E used often get more gradient. ② The loop bound (3 blocks) is plain Python, known at trace time — the loop unrolls into the jaxpr (§3.1); switch to lax.scan over stacked params when depth makes compile time/code size hurt. ③ x: (B,T,128) @ E.T: (128,46) → (B,T,46): each token's vector is dotted against every token's embedding row — similarity in embedding space becomes the logit, which is the tying intuition.

6.5 init_params: keys, scales, and what stays out of the tree

def init_params(key, vocab, d_model=128, n_layers=3, d_ff=512, max_T=256):
    def dense(key, n_in, n_out):
        return jax.random.normal(key, (n_in, n_out)) / jnp.sqrt(n_in)

    key, ek, pk = jax.random.split(key, 3)
    blocks = []
    for _ in range(n_layers):
        key, kq, kk, kv, ko, k1, k2 = jax.random.split(key, 7)   # fresh keys, every layer
        blocks.append({
            "ln1_g": jnp.ones(d_model), "ln1_b": jnp.zeros(d_model),
            "ln2_g": jnp.ones(d_model), "ln2_b": jnp.zeros(d_model),
            "attn": {"wq": dense(kq, d_model, d_model),
                     "wk": dense(kk, d_model, d_model),
                     "wv": dense(kv, d_model, d_model),
                     "wo": dense(ko, d_model, d_model)},
            "mlp": {"w1": dense(k1, d_model, d_ff), "b1": jnp.zeros(d_ff),
                    "w2": dense(k2, d_ff, d_model), "b2": jnp.zeros(d_model)},
        })
    return {"embed": jax.random.normal(ek, (vocab, d_model)) * 0.02,
            "pos": jax.random.normal(pk, (max_T, d_model)) * 0.02,
            "blocks": blocks,
            "lnf_g": jnp.ones(d_model), "lnf_b": jnp.zeros(d_model)}

All of Part I shows up here: split-per-use key discipline (seven fresh keys per layer — §1.4), fan-in \(1/\sqrt{n_{in}}\) scaling (§4.2), LN gains at ones / biases and shifts at zeros, small (0.02) embeddings. And one subtlety that bites everyone once:

Config does not belong in the params pytree

n_heads is an integer. If you store it in params, every tree.map walks over it: jax.grad tries to differentiate it, Adam tries to update it, zeros_like zeroes it. Leaves of params must be exactly the things you train — arrays, nothing else. Static configuration lives outside: a module constant, a closure, or a static_argnums argument (§3.2). That's why transformer.py has N_HEADS = 4 at module level.

Without looking: write the dense helper and the init for one block (both LNs, four attention matrices, the two-layer MLP), with correct key handling. Then explain precisely what goes wrong if n_heads: 4 is stored as a params leaf, and name the three legal homes for static config.

Seven splits per block: q, k, v, o, w1, w2 — plus the carried parent. LN params need no keys (deterministic ones/zeros).

Code as in §6.5: dense = normal(key,(n_in,n_out))/sqrt(n_in); LNs at ones/zeros (no randomness); each weight gets its own fresh subkey, parent key carried forward. With n_heads as a leaf: jax.grad attempts to differentiate an int (error, or a useless zero-gradient float), adam_init's zeros_like turns it into an array 0, and the first update "trains" your head count — at best a crash, at worst silent corruption of config. Legal homes: a module-level constant (our choice), a closed-over variable (capturing true constants is fine, §3.3), or a static_argnums argument when it must vary between calls.

6.6 cross_entropy and loss_fn

def cross_entropy(logits, targets):
    logp = jax.nn.log_softmax(logits, axis=-1)                      # (..., V)
    picked = jnp.take_along_axis(logp, targets[..., None], axis=-1)[..., 0]
    return -picked.mean()

def loss_fn(params, tokens):          # tokens: (B, T+1)
    inputs, targets = tokens[:, :-1], tokens[:, 1:]                  # the shift
    logits = forward(params, inputs)                                 # (B, T, V)
    return cross_entropy(logits, targets)

Two implementation points. Numerics: always log_softmax, never log(softmax(…)) — the fused version subtracts the max before exponentiating, immune to overflow, and never takes log(0). Gathering: we need logp[b, t, targets[b, t]] for every (b, t); take_along_axis does exactly that batched indexing — targets[..., None] lifts targets to \((B, T, 1)\) so it can index the last axis, and [..., 0] drops the singleton. (One-hot multiply-and-sum is the same math, at the cost of materializing \((B, T, V)\).)

Write cross_entropy(logits, targets) and loss_fn(params, tokens) from memory, with the shift. Why is log_softmax numerically safer than log(softmax(x)) — show the failure input — and what do the shapes look like through the take_along_axis gather?

Failure: logits like [1000, 0]. softmax overflows e^1000 → inf/inf; log_softmax computes x − max − log Σ e^(x−max).

Code as in §6.6. With logits [1000, 0]: softmax evaluates \(e^{1000} = \infty\) ⇒ nan; even mild versions underflow small probabilities to 0 ⇒ log(0) = -\infty. log_softmax rewrites as \(x - \max(x) - \log\sum e^{x - \max(x)}\): exponents are \(\le 0\), nothing overflows, the log argument is \(\ge 1\). Shapes: logp (B,T,V), targets[...,None] (B,T,1) indexes axis −1 → picked (B,T,1) → [...,0] → (B,T) → mean → scalar. The shift: inputs [:, :-1], targets [:, 1:], so position t is graded on token t+1.
