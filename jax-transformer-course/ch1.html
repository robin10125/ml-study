Chapter 1 · Thinking in JAX: Arrays, Purity & Randomness

You know PyTorch and TensorFlow. JAX will feel familiar for ten minutes — it looks like NumPy — and then deeply strange, because it inverts the central design decision of both frameworks: nothing holds state. This chapter installs the three habits everything else builds on: immutable arrays, pure functions, and explicit randomness.

1.1 What JAX actually is

JAX is two things bolted together:

  1. A NumPy clone. import jax.numpy as jnp and most of what you know works: jnp.dot, jnp.exp, broadcasting, fancy indexing for reading. Arrays live on CPU/GPU/TPU and the same code runs on all three.
  2. A set of composable function transformations. jax.grad(f) is a new function that computes \(\nabla f\). jax.jit(f) is a new function that runs a compiled version of f. jax.vmap(f) is a new function that runs f across a batch. They compose: jit(vmap(grad(f))) is ordinary, idiomatic JAX.

The price of admission: transformations only work on functions that behave like mathematical functions — output determined entirely by inputs, touching nothing else. That single requirement explains every difference from PyTorch you're about to meet.

Here is the inversion to internalize. In PyTorch, state lives inside objects: an nn.Module owns its weights, loss.backward() deposits gradients into hidden .grad fields, the optimizer mutates parameters in place, and a global RNG hides behind torch.manual_seed. In JAX, all of that state is data you pass around explicitly:

conceptPyTorchJAX
modelobject: module(x), weights insidefunction: forward(params, x), weights are an argument
parametersmodule.parameters(), mutated in placea nested dict of arrays you hold yourself; updates return a new dict
gradientsside effect: loss.backward() fills .gradreturn value: grads = jax.grad(loss_fn)(params, batch)

Nothing is lost — every capability survives — but everything hidden becomes visible. A full training loop is: params, opt_state, key go in; new params, opt_state, key come out. By Chapter 7 you will have written exactly that for a transformer.

JAX = a NumPy clone (jax.numpy) + composable function transformations (grad, jit, vmap) that require pure functions. The inversion: state lives in data you pass explicitly, not inside objects. Counterparts: a model is a pure function forward(params, x) with parameters as an argument; gradients are the return value of jax.grad(loss_fn)(params, …); an update returns a new params dict (nothing mutated); randomness comes from explicit key arguments. Everything hidden becomes an explicit input/output.

1.2 Arrays are immutable

The first habit to break: in-place assignment. JAX arrays cannot be written to:

x = jnp.zeros(5)
x[0] = 1.0          # TypeError: JAX arrays are immutable

y = x.at[0].set(1.0)   # the JAX way: a NEW array, x untouched
z = x.at[2].add(3.0)   # read-modify-write variants: add, mul, min, max, …

The .at[idx].op(value) syntax accepts everything NumPy indexing accepts — slices, boolean masks, integer arrays — and returns a fresh array, leaving the original alone. So the PyTorch idiom on the left becomes the JAX idiom on the right:

# PyTorch (in place)                # JAX (functional)
x[mask] += 1.0                      x = x.at[mask].add(1.0)
x.clamp_(min=0)                     x = jnp.maximum(x, 0.0)
buf[i] = obs                        buf = buf.at[i].set(obs)

Why this restriction? Because transformations reason about your function as a mathematical object. If f could silently modify its inputs, then grad(f) and jit(f) could not safely reorder, cache, or re-execute pieces of it. Immutability is what makes the transformations sound.

Isn't copying the whole array absurdly slow? In eager (un-compiled) code, yes, each .at[].set really copies. Inside jit-compiled code — which is where all real JAX programs run — the compiler proves the old value is never used again and turns the copy into an in-place write. You write functional code; XLA emits mutating code. You get the safety without paying for it.

Convert to JAX: (a) x[3] = 7, (b) x[x < 0] *= 0.1, (c) row[i] += g. Then answer: what does .at[].set return, what happens to the original array, and why is the apparent copy usually free in practice?

Every conversion has the same shape: x = x.at[…].something(…) — you must rebind the name, because nothing was modified.

(a) x = x.at[3].set(7); (b) x = x.at[x < 0].mul(0.1) (or x = jnp.where(x < 0, x * 0.1, x)); (c) row = row.at[i].add(g). .at[].set returns a new array; the original is unchanged (forgetting to rebind is the classic silent bug). Under jit, XLA sees the old buffer is dead and compiles the operation into an in-place update, so the functional style costs nothing in compiled code.

1.3 Pure functions: the contract

A function is pure if (1) its output depends only on its explicit arguments, and (2) it has no side effects — it doesn't mutate anything, write files, print as part of its contract, read globals that change, or consult a hidden RNG. JAX's transformations assume purity. They do not check it.

Impure code usually doesn't crash — it silently lies

This is the single most important safety fact in JAX. If your function reads a global, mutates an attribute, or appends to a list, jax.jit will not raise an error. It will trace your function once, capture whatever the global/attribute happened to hold at trace time as a frozen constant, and reuse the compiled result forever after. The print fires once and never again; the mutation happens once and never again; the "updated" global is ignored. (Chapter 3 dissects the mechanism.)

What purity means in practice for model code:

  • Everything that varies must enter as an argument: parameters, inputs, RNG keys, step counters.
  • Everything the function produces must leave as a return value: outputs, new states, metrics.
  • Out-of-place math only — which immutability (§1.2) already enforces for arrays.

You can still organize code with Python classes and closures — JAX is a library, not a language — but anything that changes over time must flow through arguments and return values, never through attributes. This is exactly why frameworks like Flax exist (they generate the pure functions for you); we build raw so that nothing is magic.

State the two conditions of purity. Then classify each as safe or unsafe to jit, with the failure mode: (a) def f(x): return x @ W where W is a module-level array that your training loop reassigns each step; (b) def g(x): print(x.mean()); return 2*x used for per-step logging; (c) def h(params, x): return forward(params, x).

JAX won't error on (a) or (b). Ask what each one does on call #2, after compilation.

Pure = output depends only on explicit arguments, and no side effects. (a) Unsafe: W is captured at trace time as a constant; reassigning the global later does nothing — the compiled f uses the original W forever. Fix: pass W as an argument. (b) Unsafe as logging: print executes only during the one tracing call (printing an abstract tracer, not numbers), then never again. The math is fine; the logging silently vanishes. Return the value instead, or use jax.debug.print. (c) Safe — everything that varies is an argument; this is the canonical shape of JAX model code.

1.4 Randomness without a hidden RNG

A stateful RNG is impure by definition: two calls to torch.randn(3) return different values, so the output doesn't depend only on the arguments. JAX's solution is to make the RNG state an explicit value — a key — that you pass in:

key = jax.random.PRNGKey(0)        # fresh key from a seed
x = jax.random.normal(key, (3,))   # deterministic function of (key, shape)
y = jax.random.normal(key, (3,))   # SAME key  ⇒  x and y are IDENTICAL

Same key in, same numbers out, every time, on every machine. Randomness becomes reproducible by construction. But then how do you ever get different numbers? You split:

key, sub = jax.random.split(key)         # one key in, two independent keys out
w1 = jax.random.normal(sub, (4, 4))
key, sub = jax.random.split(key)
w2 = jax.random.normal(sub, (4, 4))      # independent of w1

keys = jax.random.split(key, 8)          # or: split into many at once

The discipline, which every JAX program follows:

The key discipline
  1. Never use the same key twice for two different random draws — they would be perfectly correlated (identical, for same-shaped calls). This is the classic silent bug: nothing errors, your "random" init has cloned rows or your "two" dropout masks are one mask.
  2. Split, use the child, keep the parent moving: key, sub = jax.random.split(key), consume sub, carry the new key forward. The training loops in Chapters 4 and 7 thread key exactly like this, step after step.

Why go to this trouble instead of a global seed? Reproducibility (the whole program is a deterministic function of one integer), and parallelism: vmap/multi-device code can hand every lane its own key with no contention over shared RNG state and no dependence on execution order — something global RNGs fundamentally cannot do.

Write the code that draws two independent \(4\times4\) Gaussian matrices starting from jax.random.PRNGKey(42). Then: what would be wrong with passing the same key to both calls, why doesn't JAX raise an error for it, and what two properties motivate explicit keys over a global seed?

The pattern is three lines repeated: split, draw with the child, carry the parent. (Or split once into two children.)
key = jax.random.PRNGKey(42)
k1, k2 = jax.random.split(key)
a = jax.random.normal(k1, (4, 4))
b = jax.random.normal(k2, (4, 4))

Same key to both calls ⇒ a and b are bit-for-bit identical — jax.random.normal is a deterministic function of (key, shape). No error is possible because reuse is indistinguishable from intentional replay; correctness is your job (the discipline: never reuse). Motivations: total reproducibility (program = deterministic function of the seed) and parallelism (each batch element / device gets its own key with no shared mutable RNG state, independent of execution order).

Predict the output relationships (identical or independent) without running:

key = jax.random.PRNGKey(0)
a = jax.random.normal(key, (2,))
key2, sub = jax.random.split(key)
b = jax.random.normal(key, (2,))
c = jax.random.normal(sub, (2,))
d = jax.random.normal(jax.random.PRNGKey(0), (2,))

Which of a, b, c, d are equal to each other?

Splitting does not consume or modify the parent key — keys are immutable values like everything else. What is key on line 4?

a = b = d; c is independent of all of them. a and b use the very same key value — split returned new keys but didn't (couldn't) mutate key, so reusing the name reuses the numbers. d rebuilds the same key from the same seed ⇒ same draw. c uses a fresh child key ⇒ independent stream. Moral: rebind the parent (key, sub = split(key)) or you will reuse it by accident.

1.5 Small practicalities that save an afternoon

  • float32 by default. JAX defaults to 32-bit (like deep-learning practice, unlike NumPy's float64). 64-bit needs an explicit config flag.
  • Asynchronous dispatch. Operations return immediately with a "future" array while the device computes. Correct results always; but if you time code, call result.block_until_ready() or you're timing the dispatch, not the work.
  • Devices are automatic. Arrays go to the default device (GPU if present); there's no .to(device) choreography for single-device code.
  • NumPy interop. np.array(x) pulls a JAX array to host; JAX functions accept NumPy arrays and Python scalars and convert them.

A colleague benchmarks a jitted matmul like this and concludes JAX is 1000× faster than PyTorch:

t0 = time.time()
y = fast_matmul(a, b)
print(time.time() - t0)   # 0.00002 s !!

JAX returns before the device finishes. What does the returned array represent until then?

They measured dispatch — JAX queues the computation asynchronously and returns a placeholder immediately; the multiply hadn't run yet. Fix: y = fast_matmul(a, b); y.block_until_ready() inside the timed region (and time the second call, so compilation isn't included either). The dtype differs because JAX defaults to float32 (deep-learning convention), NumPy to float64.

Closed book — translate this PyTorch fragment into idiomatic JAX (eager is fine; no jit needed yet):

torch.manual_seed(0)
W = torch.randn(3, 2) * 0.1        # "the model"
def predict(x):
    return torch.relu(x @ W)
W += 0.01                           # nudge the weights in place

Your version must respect all three habits: explicit keys, weights as data, no mutation.

Three changes: the seed becomes a key passed to the init; W becomes an argument of predict; the in-place nudge becomes a rebinding.
key = jax.random.PRNGKey(0)
W = jax.random.normal(key, (3, 2)) * 0.1

def predict(W, x):                  # weights enter as an argument
    return jax.nn.relu(x @ W)

W = W + 0.01                        # new array, rebound — nothing mutated

Every piece of state is now visible: the RNG state is key, the model state is W, and "updating the model" means computing a new W and rebinding. Scale this dict-of-arrays pattern up and you have exactly how the transformer will work: forward(params, tokens), with params threaded through a functional training loop.
