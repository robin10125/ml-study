Chapter 3 · jit & vmap: Tracing, Compilation, Batching

Eager JAX is slow — every jnp op is a separate device round-trip. The speed (and TPU support, and fusion) comes from jax.jit, which compiles whole functions with XLA. Understanding the one mechanism behind it — tracing — explains every "weird" JAX behavior you will ever hit. Then vmap, the transform PyTorch users didn't know they wanted.

3.1 What jit actually does: tracing

jax.jit(f) does not read your source code. The first time you call it, JAX runs your Python function once with tracer objects in place of the real arguments. A tracer knows only its shape and dtype — e.g. f32[32,64] — not its values. Every jnp operation you apply to a tracer gets recorded; the recording (a jaxpr) is handed to the XLA compiler; the compiled binary is cached. Every later call with the same shapes/dtypes skips Python entirely and runs the binary.

@jax.jit
def f(x):
    print("tracing!", x)          # a side effect — watch it
    return (x @ x.T).sum()

f(jnp.ones((4, 4)))   # prints: tracing! Traced<ShapedArray(float32[4,4])>
f(jnp.ones((4, 4)))   # prints NOTHING — compiled code runs, Python doesn't
f(2 * jnp.ones((4, 4)))  # prints nothing — same shape/dtype, same binary
f(jnp.ones((8, 8)))   # prints: tracing! …float32[8,8] — new shape ⇒ re-trace, recompile
The three-line summary of jit
  1. Your Python runs once per input signature (shape + dtype + static values), with value-less tracers.
  2. Only operations on tracers are recorded. Everything else — prints, appends, attribute reads — happens once, at trace time, and is not part of the compiled program.
  3. New shape, new dtype, or new static value ⇒ new trace ⇒ new compilation (expensive — keep shapes fixed in training loops).

Python-level control flow still works when it depends on things known at trace time: a for loop over a fixed range simply unrolls (the loop ran in Python during tracing; the jaxpr contains the repeated body — exactly how our transformer's layer loop will compile).

First call: JAX substitutes tracers (shape + dtype, no values) for the arguments, executes your Python once, records every traced operation into a jaxpr, compiles it with XLA, caches the binary. Subsequent calls with the same signature: the binary runs directly; your Python doesn't execute. The four calls: ① prints tracing! with a tracer (first time, (4,4) f32); ② prints nothing (cache hit); ③ prints nothing — values don't matter, only shape/dtype; ④ prints tracing! again — new shape (8,8) means re-trace + recompile. Recompilation triggers: new shape, new dtype, new value of a static argument (§3.2).

3.2 Control flow on traced values: the one real error

Tracers have no values — so any Python construct that needs a concrete boolean now cannot proceed:

@jax.jit
def leaky(x):
    if x.sum() > 0:          # TracerBoolConversionError!
        return x
    return 0.01 * x

Python's if must commit to a branch during tracing, but x.sum() > 0 is a tracer — its truth value depends on runtime data the trace doesn't have. The same applies to while conditions on traced values and to int(x)/float(x) conversions. Three fixes, in order of preference:

  1. Compute both branches, select with jnp.where(cond, a, b) — element-wise, differentiable, cheap when branches are cheap. This is the workhorse: it's exactly how the causal mask will be applied in the transformer (jnp.where(mask, scores, -jnp.inf)).
  2. jax.lax.cond(pred, true_fn, false_fn, operand) — a real runtime branch compiled into the program, when the branches are expensive and you want to run only one. (Similarly lax.while_loop, lax.fori_loop for data-dependent loops, and lax.scan — Chapter 4.)
  3. static_argnums — when the "data" is really configuration (a flag, a size, a mode string): declare that argument static and JAX traces a separate specialized version per value. Configuration becomes compile-time constant; passing many different values means many compilations.
def leaky(x):
    return jnp.where(x.sum() > 0, x, 0.01 * x)          # fix 1

@partial(jax.jit, static_argnums=2)                      # fix 3: 'training' is config
def forward(params, x, training):
    ...

Why exactly does if x.sum() > 0: fail under jit while for i in range(6): works fine? Fix this function so it jits, and state when you would reach for lax.cond or static_argnums instead:

@jax.jit
def clip_step(g, max_norm):
    n = jnp.linalg.norm(g)
    if n > max_norm:
        return g * (max_norm / n)
    return g
Which of the two conditions is known at trace time? For the fix: compute both outcomes, then select.

range(6) is plain Python data, known during tracing — the loop just unrolls. x.sum() > 0 is a tracer: no value exists at trace time, so Python's if can't pick a branch ⇒ error. Fix:

def clip_step(g, max_norm):
    n = jnp.linalg.norm(g)
    return jnp.where(n > max_norm, g * (max_norm / n), g)

(Both branches are cheap elementwise math, so computing both is fine — this is also exactly global-norm gradient clipping.) Use lax.cond when branches are expensive enough that running both wastes real compute; use static_argnums when the branching value is configuration (model size, a boolean mode) that takes few distinct values — each value gets its own compiled specialization.

3.3 Closure capture: where hidden state goes to die

Now the punchline this course has been building toward since §1.3. What happens to values your function uses but doesn't take as arguments — globals, closed-over variables, self.attribute? During tracing they are real Python objects with real values, so the trace bakes them in as compile-time constants.

class Model:
    def __init__(self):
        self.W = jnp.ones((4, 4))
    @jax.jit
    def __call__(self, x):
        return x @ self.W        # self.W captured at trace time

m = Model()
m(x)                  # traces; compiled program contains W = ones
m.W = m.W * 100       # "update" the weights…
m(x)                  # …same output as before. Update silently ignored.

No error, no warning — the compiled binary doesn't know self.W exists; it has the numbers from trace time burned in. This is the precise mechanism behind the rule from Chapter 1:

The rule, now with its reason

Anything that changes between calls must be an argument. Arguments become tracers — live wires in the compiled program, fed fresh values each call. Everything else is frozen at trace time. Weights, optimizer state, RNG keys, step counters: arguments, always. (Closing over genuine constants — hyperparameters that never change, like n_heads — is fine and idiomatic.)

The Model class above trains "successfully" — the loss curve is computed from gradients against… what? Explain the mechanism (what tracing does to self.W), why no error is raised, and rewrite the class as the idiomatic JAX pattern. Which closed-over values are fine to capture?

During tracing, self.W is not a tracer. What does the trace record it as? Then: what's the only way to make a value "live" in compiled code?

self.W isn't an argument, so during tracing it's a concrete array — recorded as a constant in the jaxpr. The compiled program forever multiplies by the initial weights; later assignments to self.W change a Python attribute the binary never reads. No error is possible: capturing constants is legitimate, and JAX can't know you intended it to vary. Idiomatic rewrite:

def init(key):  return {"W": jax.random.normal(key, (4, 4))}
@jax.jit
def apply(params, x):  return x @ params["W"]   # params: argument ⇒ live

Fine to capture: true constants — config integers like n_heads, fixed hyperparameters, even fixed arrays — anything that never changes across calls.

3.4 vmap: write for one, run for many

jax.vmap(f) returns a function that runs f across a new leading axis — as if in a Python loop, but compiled into batched operations (one big matmul, not B small ones). The superpower: you write per-example logic with no batch dimension cluttering the shapes, then batch it mechanically.

def predict(params, x):          # x: (d_in,)  — ONE example, no batch dim
    return x @ params["W"] + params["b"]      # (d_out,)

batched = jax.vmap(predict, in_axes=(None, 0))
batched(params, X)               # X: (B, d_in) → (B, d_out)

in_axes says, per argument, which axis is the batch axis: 0 = map over the leading axis, None = broadcast (every lane sees the same value — the natural choice for params). out_axes (default 0) says where the mapped axis lands in the output. For pytree arguments, a single 0/None applies to every leaf.

And it composes. Per-example gradients — genuinely awkward in PyTorch, where .backward() sums over the batch — are one line:

per_example_grads = jax.vmap(jax.grad(loss_one), in_axes=(None, 0, 0))(params, X, Y)
# every leaf of per_example_grads has a leading (B,) axis

Nested vmap handles doubly-batched data; vmap of attention-over-one-head gives attention-over-all-heads. In Chapter 6 we'll mostly batch with ordinary broadcasting (matmuls handle leading axes natively, and @ batches itself), but vmap is the general tool when broadcasting gets contorted.

params is shared across the batch — which in_axes entry encodes that? And remember vmap wraps grad just as happily as it wraps the plain function.

(a) losses = jax.vmap(loss_one, in_axes=(None, 0, 0))(params, X, Y) → shape (B,). (b) g = jax.vmap(jax.grad(loss_one), in_axes=(None, 0, 0))(params, X, Y) — a pytree like params but with every leaf gaining a leading (B,) axis. (None, 0, 0): broadcast params to all lanes; map x and y over their leading axes. PyTorch's backward() computes the gradient of a summed loss — per-example gradients require hooks or B separate backward passes; in JAX, gradient-of-one-example is just a function, and vmap batches any function.

Shape puzzle, no running: f(a, b) takes a: (3,), b: (3,) and returns their elementwise product, shape (3,). What are the output shapes of:

g1 = jax.vmap(f, in_axes=(0, 0))        # called with a: (8, 3), b: (8, 3)
g2 = jax.vmap(f, in_axes=(0, None))     # called with a: (8, 3), b: (3,)
g3 = jax.vmap(f, in_axes=(0, 0), out_axes=1)   # a: (8, 3), b: (8, 3)

And: what error class do you expect if you call g1(a, b) with a: (8, 3), b: (5, 3)?

vmap adds one mapped axis of size B to the per-example result (3,). out_axes chooses where that B axis is inserted.

g1: (8, 3) — both mapped over axis 0. g2: (8, 3) — b broadcast to every lane. g3: (3, 8) — same computation, mapped axis placed at position 1 of the output. Mismatched batch sizes (8 vs 5) fail at call time: vmap requires every mapped axis to have the same length, and raises a shape/axis error before any computation runs.

3.5 Using jit well

  • Jit the biggest sensible unit — the whole training step (forward + backward + optimizer update), not individual layers. XLA fuses across everything it sees; small jits leave fusion (and dispatch savings) on the table. One @jax.jit on train_step is the entire performance story of Chapter 7.
  • Keep shapes constant. Each new shape recompiles. Fixed batch size, fixed sequence length (pad if needed) — this is why our training batches are always exactly (B, T+1).
  • Benchmark with block_until_ready(), and never time the first (compiling) call.
  • Don't jit during early debugging. Un-jitted JAX runs your Python every call: real values, working print, normal debugger. Develop eager, then add @jax.jit, then verify outputs match. (jax.debug.print works inside jit when you need it.)

Diagnose both stalls. Then state the four practical jit habits from this section.

How many distinct input signatures does the step function see per epoch?

Two signatures per epoch: (32, …) batches and one (17, …) batch — the step compiles twice; the (17,…) compilation re-happens "per epoch" only if caches are evicted, but the visible stalls are the two compilations (and every-epoch stall if the loop is also re-jitting due to, e.g., a fresh closure each epoch). Fix: drop or pad the ragged batch to 32 so exactly one signature exists. Habits: ① jit the whole train step, not pieces; ② keep shapes fixed across steps; ③ benchmark only post-compilation calls, with block_until_ready(); ④ debug un-jitted first, add jit when correct (with jax.debug.print if needed inside).
